## Medium (2)

- **Pi Brain POST needs curl 7.76+ (--fail-with-body), so it can never succeed on older curl where the base POST worked** — `src/plugins/dot-shortcuts.js:3786` (correctness): The base generator posted with plain curl -X POST, which works on any curl. The new fence always passes --fail-with-body, added in curl 7.76.0. macOS 11 (7.64.1), Ubuntu 20.04 (7.68), Debian 11 (7.74) and RHEL 8 (7.61) ship older curl. Reproduced with a wrapper that rejects the option: 'option --fail-with-body: is unknown', exit 2; every retry fails the same way, so submission is permanently broken there. Exit 2 is never named. The test requires the exact --fail-with-body string, locking the regression in. — fix: Use flags every curl has: curl -sS -o "$B.resp" -w '%{http\_code}' ... and treat any status other than 2xx as not submitted (print the body file). Name the exits and update the test to assert the portable form.
- **Fork-check search exits 0 on an HTTP error, so a degraded Pi Brain reads as 'no similar recipe'** — `src/plugins/dot-shortcuts.js:3757` (correctness): The search runs curl -sS -G with no --fail. A 502/503, a 404, a proxy error or a captive-portal page all exit 0; the prose says exit 0 prints the registry's answer, and the 'treat the fork check as not done' rule covers only non-zero exits. On a degraded network the agent finds no match in an error body and submits a new recipe instead of a fork: a failure read as nothing found. — fix: Write the status with -w '%{http\_code}' and exit non-zero unless it is 2xx, then name that exit as 'search failed: fork check not done'.

## Low (4)

- **Pi Brain search and POST have no connect or total timeout** — `src/plugins/dot-shortcuts.js:3757` (correctness): Neither curl sets --connect-timeout or --max-time. Against a stalled endpoint the search ran until an outer timeout killed it; in a session it hangs until the Bash tool's own timeout, and no exit 28 is named. — fix: Add --connect-timeout 10 --max-time 30 to both curls and name exit 28 (timed out) as a failure of that step.
- **Keep-files-and-retry advice can post the same recipe twice after an ambiguous POST failure** — `src/plugins/dot-shortcuts.js:3792` (correctness): After any non-zero POST exit the files are kept so a retry needs no rebuild. On a flaky link the server may already have stored the recipe when the client sees a timeout, a reset, or a gateway 5xx; a blind retry creates a duplicate public recipe. — fix: Say that after a timeout or a reset mid-POST (exit 28, 52, 56, or the tool being killed), the agent first searches for the exact title and resends only when the recipe is not already there.
- **Lens prose never says a diff-range git timeout (slow disk or big repo) is exit 1 or how to raise it** — `src/plugins/dot-shortcuts.js:232` (docs): diff-range exits 1 when its 60000 ms per-git-call timeout expires. The lens prose in all six workflows describes exit 1 only as 'wrong input or a broken state' and does not mention --timeout \<ms\>, while the safe-git prose does. — fix: Add to the exit-1 sentence: 'including a git call that ran past the 60000 ms default (the message names it); rerun with diff-range --timeout \<ms\>'.
- **Overnight log() starts two node processes and a git rev-parse for every output line** — `.claude/commands/.shortcuts/w-ralph-batch.md:166` (performance): With redaction on, each line claude -p prints goes through node cli.js redact (which spawns git rev-parse) and a second node -e to decode the JSON: about 100 ms per line here, closer to 0.5 to 1 s on a slow host, so several hundred lines spend minutes on logging. — fix: Redact once per candidate: capture claude -p output to a temp file, run redact --keep-lines over the whole file once, and append the decoded text to the log (keeping the failure marker for when redact fails).
