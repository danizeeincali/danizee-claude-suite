## Medium (3)

- **safe-git exit 3 from a timeout prints no JSON, but the wired text says exit 3 always prints it** — `.claude/commands/.shortcuts/w-bbs.md:124` (facts): CP4 step 2 says '3 git failed or timed out (it prints \`{ stdout, stderr, code, exit }\`)' and 'only exits 0 and 3 print that JSON'. SAFE\_GIT\_LINES (src/lib/bbs/inventory.js:494, mirrored in .claude/helpers/bbs/inventory.js) says the same. In safe-git.js:272-275, defaultGitRunner throws KitExit(..., 3) on ETIMEDOUT, ENOBUFS (output over 256 MiB) and a signal kill. cli.js turns that into a \`kit: ...\` line on stderr with nothing on stdout. Reproduced: \`safe-git --timeout 1 --dir \<clone\> -- log\` gives stdout empty, stderr 'kit: git config took longer than 1 ms and was stopped (raise it with --timeout \<ms\>)', rc=3. On slow disks, network filesystems or very large clones the 60 s default timeout is the realistic exit-3 path. Neither text mentions --timeout. — fix: Say exit 3 prints the JSON when git ran and failed, and only a \`kit:\` stderr line when git timed out, overflowed or was killed. Note that \`--timeout \<ms\>\` raises the 60000 ms default. Apply the same wording in CP4 and SAFE\_GIT\_LINES (both copies).
- **CP6 does not cover scrub exit 2 as a refusal (no JSON, nothing scanned), so the lead can read it as 'no run-path hits'** — `.claude/commands/.shortcuts/w-bbs.md:166` (correctness): scrub reports safe-git refusals (KitExit 2) as exit 2 with only a \`kit: refused:\` line on stderr and no JSON. That happens when the user's own project uses object alternates (a \`git clone --shared\` or \`--reference\` clone), has more than 100000 loose objects, has .git on a network path, or has more than 200000 tracked files. Reproduced in a \`--shared\` clone with a real hit in .claude/bbs/runs/r1/labels.jsonl: rc=2, 'kit: refused: ... borrows objects from ...', no hits list. The CP6 text treats exit 2 only as 'hits or an incomplete scan' and blocks /bc only on run-path hits, \`complete: false\` with run paths in not\_scanned, or \`truncated: true\`. On a refusal none of these fields exists, so a literal reading finds no run-path hits and proceeds to /bc. A refusal also cannot be cleared by removing hits. — fix: Add: exit 2 with no JSON and a \`kit: refused:\` line on stderr means nothing was scanned. Report the reason verbatim. It is not clean and is never read as 'no hits in this run's paths'. Treat it like exit 1 (advisory: the lead sees the reason before /bc), or block /bc. Do not tell the lead to remove hits.
- **Recording with \`"$(cat "$R")"\` silently records empty evidence when $R or $E is not set in that shell** — `.claude/commands/.shortcuts/w-bbs.md:130` (correctness): The block prints \`file=\<path\>\` and the text says 'call it \`$R\`'. The record command is then given literally as \`--evidence "$(cat "$R")"\`, followed by \`rm -f "$R" "$E"\`. Shell variables do not persist between the agent's separate Bash calls, and the block's own \`$E\` must also be set in the same command, which the text never shows. If the lead runs the record command as printed, \`cat ''\` fails on stderr and the substitution is empty. The command becomes \`--evidence ''\`; sanitizeEvidence returns null, and verdict exits 0 with no evidence and no error. Verified: with R unset, argc=2 and the evidence argument is ''. The probe's reason is lost with no non-zero exit to catch it. — fix: Show the variables bound in the same command, e.g. \`E=\<path\>; \<block\>\` and \`R=\<printed path\>; \[ -s "$R" \] || { echo 'evidence file missing or empty' \>&2; exit 1; }; node .../cli.js verdict --probe ... --evidence "$(cat -- "$R")"\`. Or tell the lead to write the literal printed path in place of $R and $E.
