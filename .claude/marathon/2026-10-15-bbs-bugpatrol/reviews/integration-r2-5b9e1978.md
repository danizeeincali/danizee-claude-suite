## High (1)

- **Marathon helper allowance uses one fixed state file that later runs inherit** — `src/plugins/dot-shortcuts.js:4785` (correctness): 4.1a opens the allowance at .claude/marathon/helper-budget.json 'once per stream (skip when the file exists)'. The path is not scoped to the run id or the stream, and nothing removes the file when a run ends. The next /w-marathon in the same repo skips 'open' and grants from the old state. Confirmed: after a run that used its steps, 'grant' returns {skip:true, reason:'steps limit exhausted'} with exit 0. The step treats that as 'the allowance is used up: do not spawn, go to CHECKPOINT 5', so every later marathon stops at its first spawn. Re-running 'open' does not help, because it exits 1 ('already exists'), which the step reads as broken state. A second stream of the same run also skips 'open' and shares the first stream's allowance, which contradicts 'covers all helper sessions of the stream'. — fix: Scope the state to the run (and stream), e.g. .claude/marathon/\<run-id\>/helper-budget-\<stream\>.json, and open it in step 4.2 when the stream is activated.

## Medium (4)

- **A grant with no amount reserves the whole allowance, so a concurrent spawn or a dead helper stops the run** — `src/plugins/dot-shortcuts.js:4785` (correctness): 'shared-budget grant --helper \<id\>' without --steps/--parts reserves everything that is available (grantFor: divisor 1 returns avail). Confirmed: after h1's grant, h2's grant returns skip:true 'steps and cost limit fully reserved by other sub-sessions'. Streams run in parallel, so the second concurrent builder or reviewer gets skip. The step then reads skip as 'used up' and goes to CHECKPOINT 5, ending the run while the allowance is unspent. The text never says to 'release' a helper that dies without spending, so its reservation stays for good. The 'spend' call is also printed without --state; run as written, it exits 1 ('--state \<file\> is required') and the reservation is never settled. — fix: Pass --steps/--cost (or --parts \<live helpers\>) on grant, add --state to the spend line, add 'shared-budget release --state \<f\> --helper \<id\>' for a helper that ends without a spend, and treat a 'fully reserved' skip as 'wait', not as 'used up'.
- **w-review claim budget opens a fixed file once, so every later review stops claim checks** — `src/plugins/dot-shortcuts.js:2613` (correctness): Step 1 runs 'shared-budget open --state .claude/kit/review-budget.json --steps 30' once per review. The file is never removed or scoped to the review. On the second /w-review in a project, 'open' exits 1 (confirmed: 'b.json already exists'). The text maps exit 1 to 'broken state, report it and start no more sub-sessions', so no claim-checking sub-session runs again after the first review. If the open error is ignored, grants come from the first review's spent state and return skip:true ('steps limit exhausted'). — fix: Use a per-review state path (e.g. include the PR number or session id), or remove the file at the end of the checkpoint; treat 'already exists' on open as a stale file to replace, not as broken state.
- **Blocking replay gate in w-review lets the check pass on invalid input or a missing kit** — `src/plugins/dot-shortcuts.js:2615` (correctness): The row 'repeated replay gate → /w-review VERIFICATION' is blocking, and the run decided that judges fail closed. Here, exit 1 (invalid or unreadable $G, e.g. a typo in the file path: confirmed exit 1 'cannot read ... ENOENT') maps to 'nothing fails the check on unreplayed evidence'. Line 2616 says the same when the kit is missing. In both cases a replayed, reproducing failure that the gate would block (exit 2) is reported as passing, and the Verification checkpoint reaches 'PASS -\> proceed'. A gate that cannot run gives the most permissive result. In w-debug, by contrast, the same exit 1 leaves the diagnosis unconfirmed. — fix: On exit 1 or a missing kit, mark the check as unresolved (FAIL with 'replay gate could not run'), fix $G and rerun, or ask the user; never let it count as PASS.
