## Medium (2)

- **Comment says 'Clear - no blocking findings' while JUnit fails and SARIF reports an error for the same input** — `src/lib/kit/render.js:212` (correctness): renderComment counts only blocking findings with disposition 'open' (line 212), but renderJunit (line 166) and renderSarif (line 97) treat every blocking finding as a failure or error whatever its disposition. Input {findings:\[{id:'x',message:'sql inj',severity:'blocking',disposition:'filed'}\]} renders the comment verdict '\*\*Clear\*\* - no blocking findings (0 advisory, 1 filed)', while the JUnit has failures="1" and the SARIF has level 'error'. A blocking finding marked needs-decision gets 'Needs a decision' in the comment and still fails the JUnit. The PR comment says there are no blocking findings while the CI check built from the same findings is red. The envelope's counts.blocking (line 82) also counts the filed one, so it disagrees with the comment too. — fix: Pick one rule and apply it in all three renderers. Either have JUnit and SARIF demote filed and needs-decision blocking findings the same way the comment does, or keep them blocking and change the comment verdict to say 'no open blocking findings (N blocking filed)'. Add a test that renders one filed blocking finding in all three formats.
- **SARIF results with no file have no locations, and GitHub code scanning rejects the whole upload** — `src/lib/kit/render.js:101` (correctness): A finding without \`file\` is a valid input and is the 'orphan' case the brief says to keep, but it becomes a SARIF result with no \`locations\` array (lines 101-105). It can also have no ruleId when \`id\` is missing (line 98). GitHub code scanning refuses such files with 'locationFromSarifResult: expected at least one location', so a single orphan finding makes the SARIF upload in the test.yml target fail. The packaged test passes a fileless finding ('orphan') and checks only the levels, so it does not catch this. — fix: When a finding has no file, emit a fallback location (for example artifactLocation.uri of the repo root or the tool's config file, or a logicalLocation plus a placeholder physicalLocation) and a fallback ruleId such as 'finding'. Add a test that every result has locations\[0\] and a ruleId.

## Low (2)

- **Orphan findings and the incomplete-run error merge into user tests in the reserved suites** — `src/lib/kit/render.js:155` (correctness): Orphan findings go into the suite 'unattributed' under the name f.id, and the incomplete error goes into suite 'run' under the name 'run-completed'. Both use the same slot map as the user's tests, so a listed test {name:'x',suite:'unattributed'} takes over orphan finding id 'x' and fails. A listed test {name:'run-completed',suite:'run'} takes over the incomplete-run error. A real test case is then blamed for a finding or error it did not produce. — fix: Keep the reserved suites separate from user suites, for example by giving them their own Map or rejecting tests\[\].suite equal to 'unattributed' or 'run' in normalize.
- **render never emits a writable SARIF or JUnit file; output is always the JSON envelope** — `src/lib/kit/render.js:267` (other): run returns { format, incomplete, counts, content }, so \`cli.js render junit \> junit.xml\` writes JSON, not XML. For SARIF it writes the envelope, not the SARIF log. Every CI caller has to extract .content with jq before upload-sarif or a JUnit reporter can read it. cli.js already supports a \`raw\` result for exactly this case. — fix: Add an --out \<file\> flag that writes content to a file (or a --raw flag that returns { raw: content }), and keep the envelope as the default.
