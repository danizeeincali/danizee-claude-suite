## Medium (2)

- **Sticky comment has no size cap, so a large review is rejected by GitHub and the comment is not posted or updated** — `src/lib/kit/render.js:233` (correctness): renderComment emits one bullet per finding with no limit. GitHub refuses issue and PR comment bodies over 65536 characters (422 'Body is too long'). Confirmed: 500 advisory findings with ordinary messages and paths render a 70776-character body. In the test.yml target the post or edit then fails, so the PR either gets no comment or keeps a stale one from an earlier run. That is the case where the reader most needs the verdict. Nothing truncates, and no test covers it. The .claude/helpers/kit/render.js copy has the same code. — fix: Cap the body below 65536 characters, for example at 60000. Always keep the marker, the verdict and the Blocking section. Truncate the later sections and add a line like '... and N more advisory findings (see SARIF/JUnit)'. Add a test that 1000 findings stay under the cap and that the marker and verdict are kept.
- **SARIF artifactLocation.uri is the raw file path, not a URI, so paths with '#', '%', spaces or backslashes produce wrong or invalid locations** — `src/lib/kit/render.js:108` (correctness): physicalLocation.artifactLocation.uri is set to f.file verbatim. SARIF 2.1.0 requires a valid URI reference. Confirmed: file 'src/c#/a b%.cs' becomes uri 'src/c#/a b%.cs'. A URI parser reads that as path 'src/c' with fragment '/a b%.cs', and '%.c' is an invalid percent-escape. Code scanning then attributes the alert to the wrong file, or the upload fails validation. Windows-style 'src\\x.js' paths are not URIs either. Real repos do have paths like these, for example C# folders, names with spaces and generated files. — fix: Normalise backslashes to '/' and percent-encode each path segment with encodeURIComponent before joining with '/' (this keeps '/' as the separator). Add a test for a path containing '#', '%' and a space.

## Low (3)

- **File paths in the comment show HTML entities inside the code span** — `src/lib/kit/render.js:211` (correctness): bullet passes f.file through md(), which turns '&' into '&amp;' and '\<' into '&lt;', and then wraps the result in backticks. Markdown does not decode entities inside code spans. Confirmed: file 'a\<b&c.js' renders as \`a&lt;b&amp;c.js\`, so the comment shows a path that does not exist. — fix: Inside the code span, skip entity-escaping and only neutralise backticks and newlines. A code span cannot forge the HTML marker, so this is safe.
- **An incomplete run with open blocking findings leads with 'Review incomplete' and leaves the blocking count out of the verdict** — `src/lib/kit/render.js:225` (correctness): When incomplete is true, the verdict is only 'Review incomplete - the run did not finish (...)', even when open blocking findings exist. Confirmed with one blocking finding and incomplete:true. JUnit and SARIF both fail on that finding, but the single verdict line does not say anything is blocking. A reader who only sees the verdict, for example in a notification preview, sees no blocking signal. — fix: Append the blocking count when it is above zero, for example 'Review incomplete - the run did not finish (timeout); 1 blocking finding so far'.
- **A clean run with no tests and no findings renders an empty JUnit file with tests="0"** — `src/lib/kit/render.js:186` (correctness): With findings:\[\] and no tests, renderJunit emits \<testsuites tests="0"\> with no testsuite elements. Common JUnit reporters treat a file with zero test cases as 'no test results found', and some configurations mark that as an error. A clean review can then show up as a broken report in the test.yml target. — fix: When there are no cases at all, emit one passing testcase, for example suite 'run' with name 'review', so a clean run reads as a pass.
