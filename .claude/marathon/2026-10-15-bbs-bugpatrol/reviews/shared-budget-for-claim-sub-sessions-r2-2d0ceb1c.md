## Medium (2)

- **Stale-lock break can steal a live lock, so two writers run at once and a spend is lost** — `src/lib/kit/shared-budget.js:306` (correctness): When the lock is older than LOCK\_STALE\_MS, each waiter that stat()ed it renames whatever is at \<state\>.lock away. Waiter A can break the stale lock and create its own fresh lock; waiter B, which stat()ed the old lock just before, then renames A's fresh lock away and takes its own. A and B both run load..save together, and the finally check (token mismatch) hides it. Confirmed: crashed-holder recovery (lock file aged 2 min, then 20 parallel \`spend --steps 1\` processes), repeated 15 times. One trial ended with spent.steps=19 of 20 and every process exited 0. This is the recovery path after a sub-agent dies holding the lock, and it brings back the round-1 lost-update bug with no error. Mirrored in .claude/helpers/kit/shared-budget.js. — fix: Break a stale lock only if it is still the same file you judged stale. Read its token/ino before the rename, rename it to a unique name, then check that the renamed file has that token/ino; if not, rename it back or treat it as live. Or use a lock dir with an owner pid and check the pid is alive. Add a test that pre-ages the lock and runs N parallel spends, asserting spent.steps === N.
- **A grant reserves the whole remainder, so parallel sub-sessions are skipped and a crashed one blocks the budget** — `src/lib/kit/shared-budget.js:192` (correctness): grantFor returns everything still available, and recordGrant reserves all of it on the helper row. The first helper granted therefore holds 100% of steps and cost. Every other model grant made before that helper spends is skipped with 'fully reserved by other sub-sessions'. Confirmed: open --steps 10 --cost 5, grant A returns {steps:10,cost:5}, then grant B returns skip:true. Fan-out, the 'several sub-agents share one allowance' use case, degrades to one model sub-session at a time. On the failure path it is worse: a sub-session that is killed or crashes before calling spend keeps its reservation forever (no expiry, no release verb). Every later model grant is then skipped until someone sends a manual \`spend --steps 0\` for that helper id, which the docs and usage do not mention. — fix: Let a grant ask for a bounded share (e.g. --steps/--cost on grant, or --parts N that splits what is available) and reserve only that share. Document and test releasing a dead helper's reservation, for example \`spend --steps 0 --outcome failed\`, or add a \`release\` command.

## Low (1)

- **Lock wait (10 s) is shorter than stale age (30 s), so calls fail for ~30 s after a crashed holder and spends are dropped** — `src/lib/kit/shared-budget.js:289` (correctness): If a process dies holding \<state\>.lock, every grant, start, stop and spend in the next ~30 s gives up after LOCK\_WAIT\_MS=10000 with exit 1 ('budget state is locked'), because the lock is not stale yet. Confirmed: with a leftover lock file, a \`spend --steps 3 --outcome failed\` failed after 10024 ms and spent stayed 0. That spend is never recorded, against 'spend is recorded at once, failures included'. The window is narrow because the lock is held only for milliseconds, but the result is lost accounting. — fix: Make LOCK\_WAIT\_MS longer than LOCK\_STALE\_MS (or shorten the stale age to a few seconds, since the lock is held only for one read-modify-write) so a waiter always reaches the stale-break path before giving up.
