## Medium (2)

- **Raw file paths in code spans let a finding forge another key's sticky-comment marker for findMarker** — `src/lib/kit/render.js:216` (security): codeSpan no longer escapes '\<', so f.file is written into the body verbatim. findMarker does a plain indexOf on the raw body, so it does not care that the text sits inside a code span. Confirmed: renderComment({findings:\[{message:'m',file:'\<!-- kit-render:security --\>'}\]}) produces a 'review' comment where findMarker(body,'security') returns {start:106,end:134}. A caller that looks for its 'security' sticky comment by scanning PR comments with findMarker will match the review comment and overwrite it. A file name like that needs no '/' and can be committed in a PR. This undoes the guarantee in the header (lines 19-20): text can never forge a marker. The line-215 comment covers rendering only, not findMarker. The same code is in .claude/helpers/kit/render.js. — fix: In codeSpan, also break the marker sequence, for example by replacing '\<!--' (or every '\<') with a look-alike such as U+FF1C. Or make findMarker match the marker only at the very start of the body, which is where renderComment puts it. Add a test that a file path containing another key's marker is not found by findMarker.
- **The comment cap does not cover the verdict line, so a long incomplete-run reason still produces a body GitHub rejects** — `src/lib/kit/render.js:233` (correctness): The 60000 cap only stops bullets from being added. The marker and verdict are always emitted in full, and n.reason is put into the verdict with no length limit. Confirmed: renderComment({findings:\[\],incomplete:true,reason:'x'.repeat(70000)}) returns a 70077-character body, over GitHub's 65536 limit, so the sticky comment is not posted or updated. This angle makes a long reason likely: when the network is degraded, reason often carries a proxy or 5xx HTML error page or a stack trace. That is exactly the incomplete run the reader most needs to see. — fix: Truncate the reason in the verdict, for example to 500 characters with a trailing '...', and say the full text is in the SARIF notification or the JUnit error. Add a test that a 70000-character reason keeps the body under COMMENT\_CAP.

## Low (3)

- **One oversized blocking bullet hides every later blocking finding while advisory findings are still shown** — `src/lib/kit/render.js:251` (correctness): The loop over each section uses break at the first bullet that does not fit. Later, smaller bullets in that section are never tried, but the next sections go on adding bullets. Confirmed: one blocking finding with a 59900-character message, then a short blocker, then an advisory finding. The output is '### Blocking (2)' / '... and 2 more blocking findings', and '- \*\*a1\*\* adv' is listed. So the short real blocker is hidden while the advisory is shown. This goes against the r2 fix's aim of always keeping the Blocking section. — fix: Use continue instead of break, so a bullet that does not fit is skipped and later bullets are still tried. Or truncate a single bullet that is too long to a fixed length before checking the cap.
- **fileUri throws an uncaught URIError on a path with a lone surrogate, and SARIF rendering crashes** — `src/lib/kit/render.js:99` (correctness): encodeURIComponent throws 'URI malformed' on a lone UTF-16 surrogate. A JSON input with file 'a\ud800b.js' passes normalize, then renderSarif throws a URIError instead of a KitExit or a rendered file. Confirmed with a node one-liner. The XML path already maps lone surrogates to U+FFFD (line 128), so SARIF is the only format that crashes on this input. — fix: Before encoding, replace lone surrogates with U+FFFD, for example with s.toWellFormed() on Node 20+ or a regex. Or catch the error and fall back to an encoded U+FFFD.
- **Windows absolute paths become a bogus relative URI 'C%3A/...'** — `src/lib/kit/render.js:99` (correctness): The r2 fix turns backslashes into '/' and encodes each segment, but it leaves absolute drive-letter paths alone. That is what tools on Windows runners often emit. Confirmed: 'C:\repo\src\x.js' becomes uri 'C%3A/repo/src/x.js', which code scanning reads as a repo-relative folder named 'C:', so the alert is attached to a file that does not exist. — fix: Detect /^\[A-Za-z\]:\[\\/\]/ and emit a file:///C:/... URI with only the path segments encoded, or refuse absolute paths in normalize. Add a test for a drive-letter path.
