## Medium (3)

- **A scope named like an Object.prototype key (constructor, toString, \_\_proto\_\_) crashes visit** — `src/lib/kit/triage.js:336` (correctness): state.scopes is a plain object, so \`state.scopes\[scope\] || (...)\` returns the inherited Object.prototype member for scopes such as 'constructor', 'toString', 'valueOf' or '\_\_proto\_\_'. \`sc.sessions\` is then undefined and \`sc.sessions.includes\` throws. Confirmed: a visit with scopes \['toString'\] or a violation on scope 'constructor' exits 1 with 'kit: Cannot read properties of undefined (reading \'includes\')' and records nothing. Valid input (a module or command named constructor) is rejected with a raw TypeError and the whole visit is lost. — fix: Use Object.hasOwn(state.scopes, scope) (or a null-prototype object / Map on load) before reusing an entry; add a test with scope 'constructor'.
- **Lock holder is broken as stale after 30s while still working, so a large visit can lose writes** — `src/lib/kit/triage.js:74` (correctness): The holder never refreshes the lock's mtime, and a waiter breaks any lock older than LOCK\_STALE\_MS (30s). visit is quadratic (Object.values(state.records) per candidate plus scopes x records in the absence loop): measured 2s for 2000 violations on distinct scopes, 11s for 5000, and a 20000-violation visit (within MAX\_VIOLATIONS) ran past 120s. Any visit longer than 30s with a concurrent visit/decide waiting gets its lock removed; the waiter loads the old state and both save, so one run's records and decisions are silently lost, which the header promises cannot happen ('parallel writers all keep their writes'). — fix: Touch (utimes) the lock periodically while fn runs, or make the stale age far longer than the worst-case visit; also index records by scope+rule once per visit to remove the quadratic scans.
- **Stale-lock path busy-spins with no sleep and bypasses the wait bound** — `src/lib/kit/triage.js:114` (correctness): When the lock is stale, the loop calls breakStale and \`continue\`s immediately, before the LOCK\_WAIT\_MS check and without sleeping; the same happens when readToken returns null. If a crashed breaker left a fresh \`\<state\>.lock.break\`, breakStale returns at once and the waiter spins at full CPU until the break file is 60s old. Confirmed with a stale lock and a 55s-old break file: 5.0s wall, 4.4s CPU (user+sys). If the stale lock can never be read or removed (e.g. it is a directory or unreadable), the loop never reaches the timeout and the run hangs forever instead of failing with 'locked by another run'. — fix: Sleep before retrying after a stale-break attempt and apply the LOCK\_WAIT\_MS deadline on every iteration, not only the fresh-lock branch.

- **State path errors from mkdir surface as raw errno text** — `src/lib/kit/triage.js:101` (correctness): withLock and saveState call fs.mkdir outside any try, so a --state whose parent is a file yields 'kit: EEXIST: file already exists, mkdir .../f' with no mention of the triage state, unlike the wrapped 'cannot read/write triage state' messages elsewhere. — fix: Wrap the mkdir in withLock/saveState and rethrow invalid(\`cannot create directory for triage state ${file}: ...\`).
