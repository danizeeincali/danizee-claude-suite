## High (1)

- **Stale-lock path skips the wait cap and the backoff, so a failed break loops forever at full CPU** — `src/lib/kit/shared-budget.js:371` (correctness): When the lock is older than LOCK\_STALE\_MS, withLock calls breakStale and then \`continue\`. That jumps past both the LOCK\_WAIT\_MS check and the sleep. breakStale returns quietly when it cannot create \<state\>.lock.break: any non-EEXIST error (EROFS, EACCES, EDQUOT/ENOSPC), or EEXIST from a break file younger than 60 s. Nothing is removed, so the loop runs again at once. Confirmed: a leftover lock aged 2 min plus an open() of the .break path that fails with EROFS gave a \`spend\` that was still spinning after 60 s, with 155,113 break attempts and no exit. The documented bounded 45 s wait is never reached. A realistic case is a host that crashes holding the lock and then remounts the filesystem read-only (errors=remount-ro). open(lock,'wx') still returns EEXIST there, and every grant, start, stop and spend then hangs forever instead of exiting 1. A break file left by a dead breaker also makes every waiter hot-spin for up to 60 s, past the 45 s cap. Mirrored in .claude/helpers/kit/shared-budget.js. — fix: After breakStale, fall through to the same LOCK\_WAIT\_MS check and backoff sleep as the normal wait path instead of \`continue\`. Treat a non-EEXIST error from opening the break file as fatal and exit 1 with 'cannot lock'. Add a test that stubs the break-file open to fail and asserts the call exits within LOCK\_WAIT\_MS.

## Medium (1)

- **Lock staleness compares the local clock with the file mtime, so clock skew on a shared or network filesystem breaks live locks and loses spend** — `src/lib/kit/shared-budget.js:329` (correctness): ageOf computes Date.now() - st.mtimeMs. On NFS/SMB the mtime comes from the server's clock, and sub-agents on several hosts have their own clocks. A waiter whose clock runs more than 30 s ahead sees every fresh lock as stale. breakStale's token re-check passes, because the live holder still owns that token, so the waiter removes a live lock and two writers run load..save together. The same happens when a degraded mount stalls a holder for more than 30 s. Confirmed by simulating a client clock 60 s ahead (Date.now offset via --import): 30 parallel \`spend --steps 1\` processes, half of them skewed, ended at spent.steps of 21, 25, 19, 24, 23 and 22 over six trials. Every process exited 0. The unskewed control recorded 30/30 each time. The round-1 lost-update bug returns silently in the multi-host setup that a shared allowance exists for. Mirrored in .claude/helpers/kit/shared-budget.js. — fix: Judge staleness only from the local clock: call a lock stale when the same token has stayed unchanged for LOCK\_STALE\_MS of this waiter's own elapsed wait. Alternatively, store the holder's host and pid in the token and break only a lock whose pid is dead on the same host. Add a test that sets the lock mtime into the future or past while a holder is live, and assert that no spend is lost.
