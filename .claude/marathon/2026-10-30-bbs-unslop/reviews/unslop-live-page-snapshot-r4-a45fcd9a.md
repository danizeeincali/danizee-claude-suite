## High (4)

- **Comment scanning differs from the HTML parser: script-made \<!--\> comments let on\* handlers through to the copy** — `src/lib/kit/page-snapshot.js:252` (security): scanHtml ends a comment at the next literal '--\>' (indexOf from lt+4). The HTML parser also ends a comment at '\<!--\>', '\<!---\>' and '--!\>'. outerHTML writes comment data unchanged, so a page script that runs document.body.appendChild(document.createComment('\>\<img src=x onerror="..."\>')) is serialized as '\<!--\>\<img src=x onerror="..."\>--\>'. scanHtml reads all of that as one comment and never looks at the img, so the onerror attribute stays in page.html. A browser reads '\<!--\>' as an empty comment and then parses a real \<img\>. I probed it with a file:// page: the onerror in the saved page.html ran when the copy was opened (window.\_\_y was set). That breaks the stated promise 'Nothing runs when the copy is opened', and any page captured with --allow-remote can trigger it. — fix: Make the comment branch follow the parser's end rules: '\<!--\>' and '\<!---\>' end at once, otherwise stop at the first '--\>' or '--!\>'. Better still, have snapshotDom drop or neutralize comment nodes in the clone, for example by replacing '-' and '\>' in their data, so a comment can never hide markup.
- **noscript raw text plus the keep-the-rest-verbatim fallback leaves \<script\> in the copy** — `src/lib/kit/page-snapshot.js:295` (security): With scripting on, Chromium serializes \<noscript\> content as raw text. RAW\_TEXT (line 223) leaves out noscript, and when scanHtml meets an unclosed construct it stops and copies the rest of the document unchanged (line 252 when no '--\>' follows, line 295 when a tag is unclosed). Plain static markup such as '\<noscript\>\<!--\</noscript\>\<script\>window.\_\_x=1\</script\>\<p onclick="x()"\>' therefore puts '\<!--' inside noscript, the walk stops there, and every later \<script\> and on\* handler is written into page.html as is. I probed it with a file:// page that has no script tricks: window.\_\_x was set when the saved copy was opened. The cleanup fails open, and any remote page can use this. — fix: Add noscript to RAW\_TEXT, the same way the serializer treats it. Make scanHtml fail closed: when a comment or tag is unterminated, drop the remainder or throw, never copy it verbatim. Add a test that asserts no '\<script' and no ' on\*=' survive these inputs.
- **WebRTC (STUN/TURN) skips every network guard and reaches private hosts in remote mode** — `src/lib/kit/page-snapshot.js:707` (security): The request route, the WebSocket route and the CDP Fetch guard only see HTTP and WebSocket traffic. RTCPeerConnection ICE traffic goes past all three. In remote mode the browser is launched with only --no-proxy-server, so a page's script can make it open TCP connections (TURN ?transport=tcp) and send UDP (STUN) to any address. I probed a remote-mode page at http://127.0.0.2 that created an RTCPeerConnection with turn:127.0.0.3:18094?transport=tcp and stun:127.0.0.3:18095. The listener on 127.0.0.3 logged 'TCP connect' and two UDP packets during the capture, and blocked\_origins did not list them. The doc's claim that no request may reach a loopback, private or link-local host does not hold, and a page can use this to probe ports on the internal network or 169.254.169.254. In local mode the same path reaches any IP literal, so the claim that everything else is blocked at the browser fails there as well. — fix: Turn WebRTC off in the capture browser: add a ctx.addInitScript that deletes RTCPeerConnection, webkitRTCPeerConnection and RTCDataChannel (it runs in every frame, about:blank included), and/or launch with --force-webrtc-ip-handling-policy=disable\_non\_proxied\_udp together with a dead proxy for WebRTC. Add a test with a local TURN/STUN listener on 127.0.0.x that asserts no connection reaches it.
- **page.evaluate(snapshotDom) has no deadline, so a busy page hangs the capture past --timeout-ms + 6 s** — `src/lib/kit/page-snapshot.js:900` (correctness): This round says the deadline covers every wait, but the DOM pass after the screenshot (line 900) is awaited with no bound. The per-pending-stylesheet privateUrl DNS checks at line 911 also have no bound. When the page's main thread is busy after the screenshot, evaluate never returns. I probed it with a file:// page that runs setTimeout(() =\> { for(;;); }, 520..540 ms) and --timeout-ms 2000: the capture was still running when I killed it at 30 s, against a stated limit of 8 s. A hostile or very heavy remote page can therefore hang the verb and the agent workflow that calls it with no end, which contradicts the documented 'A capture ends within --timeout-ms plus 6 s'. — fix: Wrap the snapshotDom evaluate in bounded(..., Math.max(SCREENSHOT\_FLOOR\_MS, left()), null) and throw exit 1 ('the page did not answer in time') on null. Bound the hostVerdict lookups the same way, treating a timeout as private. Add a test with a page that busy-loops after the screenshot.
