## High (1)

- **fonts.ready wait has no bound: a stalled late font hangs capture forever** — `src/lib/kit/page-snapshot.js:806` (correctness): After the settle, capture runs page.evaluate(() =\> document.fonts.ready) with no timeout and nothing tied to the --timeout-ms deadline. If a web font is requested after the load event (text that gets a font-family once it renders, which is common in SPAs, or content revealed later) and its body stalls, which is normal on a degraded network, fonts.ready never resolves and the verb hangs. Probe: a 127.0.0.1 page whose h1 switches to an @font-face family 20 ms after load, with the font sending headers plus 10 bytes and then stalling. \`capture --timeout-ms 3000\` sat in this evaluate until an outside \`timeout 120\` killed it. Instrumented copy: 'fonts start' at +3.8 s, the evaluate returned only when the browser was torn down 56 s later. The header (lines 28-31) says --timeout-ms bounds the load, the settle and every asset body wait together. The other post-load waits also ignore the deadline: settle is Math.min(timeout, 10000) and then Math.min(timeout, 5000) for --full-page, not the time left, and the screenshot has a fixed 15000 ms. So even a run that does not hang can take about timeout + 30 s. — fix: Take every post-goto wait from the deadline that remains: race fonts.ready against a timer inside the evaluate (for example Promise.race(\[document.fonts.ready, new Promise(r =\> setTimeout(r, ms))\])) and set networkIdle-style flags when it runs out. Pass deadline - Date.now() (with a small floor) to both settle calls and to the screenshot timeout. Add a test with a stalled post-load font that must finish within --timeout-ms plus a margin.

## Medium (1)

- **Stalled asset in the initial markup fails the whole capture (exit 1, nothing written)** — `src/lib/kit/page-snapshot.js:795` (correctness): page.goto uses waitUntil:'load', and the load event waits for every image, stylesheet and font the document requested before load. One asset in the original HTML whose body stalls (a slow CDN on a degraded network, a chunked image that never ends) makes goto throw 'Timeout exceeded', and the verb exits 1 with 'could not load' and writes no files. Probe: \<img src=/ok.png\>\<img src=/stall.png\> on 127.0.0.1, with stall.png sending 4 bytes and then nothing; \`capture --timeout-ms 3000\` gave exit 1 and no out dir. The header (lines 28-31) promises that a body still unfinished when the budget is spent, 'a streaming or stalled image, say', is dropped and listed in skipped, and that the files are still written with exit 0. The r2 test covers only an image added after load (test line 855), so the common case goes untested. — fix: Navigate with waitUntil:'domcontentloaded' (or catch a goto TimeoutError once a response has been committed) and then wait for 'load' with the time left, setting a load/network\_idle flag instead of failing. The existing body-deadline path then marks the stalled asset BODY\_LATE. Add a real-capture test with a stalled \<img\> in the initial markup.
