## High (1)

- **--allow-remote lets the remote page reach loopback and private hosts, and their response bodies are inlined into page.html** — `src/lib/kit/page-snapshot.js:95` (security): In remote mode allowRequest passes any http(s) URL, and the browser starts with no resolver rules (line 515). That means a remote page (or a redirect, or its scripts doing GETs or top-level navigation before load) can make the user's browser request http://127.0.0.1:\*, 10/8, 192.168/16 or 169.254.169.254. Probe: I served a page on 127.0.0.2 (classified as remote) that links a stylesheet at http://127.0.0.1:PORT/secret. \`capture --allow-remote\` returned exit 0, the loopback server logged the request, and its text/plain body 'AWS\_SECRET=hunter2-from-loopback' was written verbatim into snap2/page.html, because the cross-origin sheet takes the pending path and the captured body is inlined. The user agreed to one live URL, not to the page probing their local services or cloud metadata and copying the replies into a file they will go on to share. — fix: In remote mode, refuse requests (and redirects and navigations) whose host is localhost, loopback (127/8, ::1), private (10/8, 172.16/12, 192.168/16, fc00::/7), link-local (169.254/16, fe80::/10) or 0.0.0.0, and record each in blocked\_origins. Add a test where a 127.0.0.2 page asks for a 127.0.0.1 asset.

## Medium (3)

- **\<embed\>/\<object\> survive the copy: embedded HTML runs script when page.html is opened, and object data= is left relative** — `src/lib/kit/page-snapshot.js:286` (security): transformHtml strips \<script\> and \<iframe\> but leaves \<embed\> and \<object\> alone. embed src is absolutized and kept (URL\_ATTRS), so the saved copy loads that document and runs its scripts. Probe: a file:// page with \<embed src=obj.html type=text/html\>, where obj.html sets parent.document.title. Opening snap/page.html gave the title 'PWNED-OBJ'. That breaks the header's promise that 'Nothing runs when the copy is opened', and in a remote capture it is live remote code. The attribute data= is also missing from URL\_ATTRS, so \<object data=logo.svg\> stays relative to the output folder, and a common SVG-logo-in-object disappears from the copy. — fix: Treat embed, object, frame and frameset like iframe: SKIP them and add a skipped entry. Or, if you keep them, inline only image types and drop any whose type or target is HTML or SVG document content. Add 'data' to the URL attributes that get absolutized.
- **--theme does not rewrite media= attributes, so a dark-only stylesheet still applies in a --theme light copy** — `src/lib/kit/page-snapshot.js:343` (correctness): forceScheme runs only over CSS text. The media attribute carried over from \<link media\> (buildSnapshot line 343, snapshotDom line 398) and the media attribute of an existing \<style\> are left untouched. Probe: \<link rel=stylesheet href=dark.css media="(prefers-color-scheme: dark)"\> captured with --theme light gives \<style media="(prefers-color-scheme: dark)"\>, so anyone opening the copy with a dark OS theme sees dark styles. Splitting light and dark into separate media-linked files is a common pattern, and the brief says the theme is forced by rewriting media queries. The existing --theme test covers only @media inside the sheet. — fix: Run forceScheme over the media value on \<style\>, \<link\> and \<source\> in transformHtml and in the pending replacement. Add a test with a media-attributed dark sheet under --theme light.
- **Packaged capture runs with no egress guard, and the zero-egress tests do not cover it** — `test/kit-unslop-live-page-snapshot-packaged.test.js:50` (test-quality): Dropping the preload is disclosed, but the comment says 'the preload runs above prove the Node side'. Those runs only reach the refusal and arg-parsing paths, never a launch, the route handler, response capture or file writing, so the one packaged run that does real I/O has no egress guard on Node or browser. The final test 'ends with zero egress (the preload-guarded runs above)' (line 67) reads the same log the first test already checked, and no guarded run happens in between, so it can never fail. The capture's \`blocked\_origins == \[\]\` check (line 58) would also pass with the browser blocker deleted, because the fixture page has no non-local references. As written, egress\_zero\_unslop-live-page-snapshot is not measured for the capture path. — fix: Keep NODE\_OPTIONS for the capture and let the preload allow just the resolved Playwright Chromium executable, for example through an env var holding pw.chromium.executablePath(). Add a remote reference such as http://blocked.invalid/x.png to the fixture and assert that it shows up in blocked\_origins and that pkg.egress() is still \[\].

## Low (4)

- **Pending-sheet substitution is O(pending x document size), and file mode builds twice** — `src/lib/kit/page-snapshot.js:347` (performance): Each pending stylesheet runs html.split(marker).join(rep) over the whole document. For file:// pages every linked sheet is pending, and buildSnapshot runs twice (line 602). Measured on an 8 MiB DOM: 0 pending 0.66 s, 300 pending 3.1 s, 1000 pending 9.4 s per build. With realistic counts (under about 30) the cost is small, but it grows with the input instead of staying linear. — fix: Do one replace with a regex /\<style data-snapshot-pending="(\d+)"\>\<\/style\>/g and a map lookup, and cache the result across the two file-mode builds.
- **assert.rejects result is swallowed by .catch(() =\> {})** — `test/kit-unslop-live-page-snapshot.test.js:105` (test-quality): In 'with --allow-remote a remote http(s) URL passes the policy and reaches the launcher', the trailing .catch(() =\> {}) discards any failure of the assert.rejects, so the rejection check can never fail. Only spy.resolved === 1 is really asserted. — fix: Drop the .catch and await assert.rejects(...) with the exact expected error.
- **blocked\_origins records the string "null" for blocked file:// requests** — `src/lib/kit/page-snapshot.js:486` (correctness): new URL('file:///...').origin is 'null', so a blocked file sub-frame or a blocked file request in http mode shows up in the manifest as blocked\_origins:\["null"\]. That is what my file:// probe with an \<embed\> produced, and it tells the reader nothing. — fix: For file: URLs, record 'file://' (or the path) instead of URL.origin.
- **Stylesheet links that failed, were blocked or are disabled are kept as live links with no skipped entry** — `src/lib/kit/page-snapshot.js:390` (docs): When l.sheet is null (blocked by the local policy, failed to load) or the link is disabled or alternate, the \<link\> stays in the copy with an absolute href. The copy then fetches it when opened, and the manifest's skipped list does not mention it. Only the pending path records 'linked instead'. — fix: Add a skipped entry for these links (or drop them) so the manifest matches what the copy will request.
