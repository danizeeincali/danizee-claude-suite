## High (1)

- **JSX input: code after the first tag is scanned as visible copy** — `src/lib/kit/slop-audit.js:226` (correctness): visibleText (jsx) blanks only the text before the first TAG\_RE match. After that, seg() blanks only brace groups that open and close inside one tag-to-tag segment and nest at most two levels deep. A function body broken up by JSX tags, top-level statements, or a TS generic (useState\<string\>, forwardRef\<HTMLButtonElement, Props\>, Array\<string\>, all matched as tags) therefore reaches the copy detectors as raw code. Probe: a plain two-component .jsx file (Header returns \<h1\>Projects\</h1\>; Footer has \`const port = 1234;\` and \`throw new Error('year is required!')\`) gives fake-data on line 6 and exclamation-marks on line 7, and \`scan --strict --file b.jsx\` exits 2. A shadcn-style forwardRef Button gives the same false hits. The header promises that copy signs read visible text only, and the workflows block on --strict, so ordinary component files fail the gate because of their code. — fix: For jsx, take visible text only from JSX children: the text between a tag's '\>' and the next '\<' or '{' while inside an element, with a depth count of open and close tags. Blank everything outside elements and every {...} expression. Do not treat a '\<Ident...\>' that follows an identifier or '(' as a tag. Add a regression test with two components, a TS generic and an Error('...!') string, and assert zero copy hits.

## Medium (2)

- **Markdown fence closing ignores fence length and info string** — `src/lib/kit/slop-audit.js:189` (correctness): maskCode closes a fence on any line that starts with three or more of the same fence character. CommonMark requires the closing fence to be at least as long as the opener and to carry no info string. So a \`\`\`\`md block that shows a \`\`\`js example ends at the inner \`\`\`, and a line '\`\`\`js' inside a block is taken as a close. Code after that point is then scanned as prose. Probe: '# T\n\n\`\`\`js\nconst a = "x!";\n\`\`\`js\nWelcome back!\n\`\`\`' on stdin reports greeting-headline and exclamation-marks on line 6, which is inside the code block. Docs that show markdown or code samples are a normal input for this verb. — fix: Record the opener's character and length. Close only on a line matching ^ {0,3}(char){len,}\[ \t\]\*$. Add a nested-fence test.
- **A README that opens with an HTML block is sniffed as html, so its fenced code is scanned** — `src/lib/kit/slop-audit.js:495` (correctness): sniff returns md only when the text does not start with '\<' (\`!/^\<\[a-z\]/i.test(t)\`). Many READMEs open with a centred logo block such as \<p align="center"\>\<img ...\>\</p\> and then use # headings. Those are sniffed as html, and --file ignores the .md extension by design, so the markdown masking (fences, inline code) never runs. Probe: such a README.md with a \`\`\`sh fence containing echo "done!" and inline \`x!\` gives format html and exclamation-marks hits on lines 8 and 11, both of which are code. Without --format md the user gets wrong hits, and --strict blocks on them. — fix: Let a leading run of HTML block lines fall through to the markdown check. For example, test the md signals on the text with leading HTML blocks stripped, or count a line-start '# ' heading or fence anywhere in the text as md even when the text opens with a tag. Add a test for a README that starts with a logo \<p\>.
