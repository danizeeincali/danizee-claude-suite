## Medium (2)

- **lineOf rescans the input from offset 0 for every finding, so lint time is quadratic** — `src/lib/kit/sample-content.js:64` (performance): add() at line 117 calls lineOf(src, idx), which counts newlines from 0 to idx on every call, so a run costs input length times finding count. Measured with lint(): a 1.9 MB markdown doc with 4,000 round-figure findings (one '$1,000 for 500 seats' line every 10 lines) took 11.1 s, and 1 MB with 55,000 findings ('We use 100% of it.' repeated) took 80 s. Both are well under the 8 MiB cap the verb accepts, so a large spec or a generated sample page under the cap can make the advisory linter look hung. — fix: Build the newline offsets once per lintText call (an array of indices of '\n') and binary-search it in add(), or sort findings by index and walk forward once. Add a timing-bounded test, for example a 2 MB input with a few thousand findings finishing in under 1 s.
- **vague-error counts words that describe the failure as a next step** — `src/lib/kit/sample-content.js:59` (correctness): NEXT\_STEP matches action words anywhere in the rest of the line and the next line, including words that only say what failed. Checked with lint(..., {rules:\['vague-error'\]}): 'Something went wrong while we tried to add your card.' gives 0 findings ('add'), 'Something went wrong with your sign in.' gives 0 ('sign in'), and 'An error occurred. Please' gives 0 ('please'). These are exactly the vague error messages with no next step that the contract says to flag, and they are common in real failure copy, so the rule misses them without any notice. — fix: Look for a next step only after the end of the vague phrase's sentence (text after the first . ! or ?, or on the next line), and match imperative phrases such as 'try again', 'check your', 'contact' or 'refresh' instead of bare words like add, use, see and please. Add the three strings above as negative cases in the vague-error test.

Measured: '\<b\>x\</b\>' plus '\<script ' x25,000 (about 200 KB) takes 5.0 s, and '\<a href=x\>' x25,000 takes 1.1 s. At the 8 MiB cap the same input would run for hours, a hang on malformed or truncated HTML. — fix: Find each closer with indexOf from the opener, and when it is missing blank to the end of the input once and stop, instead of retrying the regex at every later opener.
- **Deeply nested JSON overflows the recursive walker and fails with an unclear error** — `src/lib/kit/sample-content.js:208` (correctness): JSON.parse accepts deep nesting, but lintJson's value() recurses once per level. '\['.repeat(20000) + '\]'.repeat(20000) (40 KB, which detectFormat sniffs as JSON) throws RangeError 'Maximum call stack size exceeded'. It is not a KitExit, so cli.js prints 'kit: Maximum call stack size exceeded' and exits 1. The message does not name the input or say what was wrong with it. — fix: Walk with an explicit stack, or catch RangeError in lint() and throw bad('input JSON is nested too deeply'). Add a test for that case.
