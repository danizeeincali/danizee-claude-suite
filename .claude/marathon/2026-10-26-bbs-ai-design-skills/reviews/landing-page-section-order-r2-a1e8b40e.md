## Medium (2)

- **Same text gives a different result on stdin than via --file when it opens with an HTML block or a comment** — `src/lib/kit/landing-sections.js:181` (correctness): --file takes its type from the extension (line 220), but stdin uses sniff(), which looks only at the first tag. So the result still depends on how the input arrived, which breaks the rules.md 'Input reading' rule. I confirmed both directions. (1) A markdown spec that starts with a common banner, '\<div align="center"\>\<img ...\>\</div\>' followed by ## Hero / ## Benefits / ## Final CTA: via --file s.md, found is \[hero, benefits, final-cta\] and mirrors is true. On stdin it is read as HTML, found is \[\] and every must section is missing. (2) An HTML page that starts with a comment ('\<!-- built by x --\>' before \<!doctype\>), or with \<head\>, \<article\>, \<footer\> and so on: via --file p.html, found is \[hero, final-cta\]. On stdin it is read as markdown and found is \[\]. Either way a real page gets a wrong 'missing everything' result. No test covers this. — fix: Pick the type from the text alone on both paths: skip leading comments and whitespace, and treat the text as HTML only when it has \<!doctype\>/\<html\> or contains no markdown heading outside fenced code. Use the same rule for --file too, or add a --format flag. Add a stdin == --file test for a .md that starts with \<div\> and for a .html that starts with a comment.
- **Quadratic regex scan on malformed HTML: inputs well under the 8 MiB cap can hang** — `src/lib/kit/landing-sections.js:115` (performance): TAG's attribute part ((?:\[^\>"'\]|...)\*) can run past '\<', so every '\<' that has no later '\>' scans to the end of the input and then backtracks. htmlLabels (line 145) does the same for each \<a\>/\<button\> that is never closed: its lazy \[\s\S\]\*? runs to the end of the body. Measured: '\<div id="hero"\>' + '\<a'.repeat(20000) (40 KB) takes 3.5 s, and doubling the input roughly quadruples the time. In the hero body, 20000 unclosed '\<a href=x\>' take 1.7 s. At the advertised 8 MiB cap, that kind of malformed or truncated input runs for hours instead of finishing or exiting 1, so the byte cap does not bound the work. — fix: Exclude '\<' from the unquoted attribute class (e.g. \[^\<\>"'\]), so a scan stops at the next tag, and bound the label scan per tag (e.g. stop at the next '\<a'/'\<button' or a section boundary). Add a timing test with a large run of unclosed tags.
