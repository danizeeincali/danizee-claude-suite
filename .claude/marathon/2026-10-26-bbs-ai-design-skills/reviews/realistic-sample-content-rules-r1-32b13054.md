## Medium (4)

- **Format sniffing depends on how the input arrived (file vs stdin)** — `src/lib/kit/sample-content.js:239` (correctness): Input reading rule: --file x.md and the same text on stdin must give the same result. Here the format comes from the extension for --file, but stdin is guessed from a short list of leading tags. Two cases checked: (1) a README that opens with '\<div align="center"\>' and then has '# Get Started With Our Product' gets the title-case finding as --file x.md, but on stdin it goes into HTML mode, markdown headings are skipped (headings() only reads them when !isHtml), and the finding is lost. (2) HTML that opens with '\<p\>' on stdin is treated as plain text, so style="width:100%" is flagged as a round figure and the \<h2\> Title Case heading is missed. As a .html file the same text gives \[hype, title-case\]; on stdin it gives \[hype, round-figure\]. The same split happens for JSON at line 233 (sniffed only when there is no extension). — fix: Decide the format from the text alone, or from an explicit --format flag, the same way for both inputs. Also read markdown headings even when HTML tags are present. Add a test that lints the same text through --file and stdin and gets the same findings.
- **stdin and --file reads are not bounded; the cap is checked only after the whole input is in memory** — `src/lib/kit/sample-content.js:263` (correctness): io.stdin() is called with no maxBytes, so cli.js readStdinBytes reads until EOF (limit Infinity). Only then does Buffer.byteLength check 8 MiB, so a large or endless pipe uses unbounded memory or hangs. The rule requires io.stdinBytes({ maxBytes: MAX + 1 }). The --file path (line 260) checks with stat and then calls fs.readFile with no limit, so a file that grows after the stat is read in full. The unit test drives a fake io.stdin with a string, so the rule's required stdinBytes tests (a multibyte over-cap case and a happy path) are missing. — fix: Read stdin with io.stdinBytes({ maxBytes: MAX\_BYTES + 1 }), check buf.length, then decode. Read the file through a handle with a bounded read of MAX\_BYTES + 1. Add unit tests through stdinBytes, including multibyte text over the cap.
- **--file "" silently falls back to stdin; a repeated flag silently wins last** — `src/lib/kit/sample-content.js:222` (correctness): parse() only refuses an undefined value or a value starting with '--'. With --file '', flags.file is '', which is falsy, so run() reads stdin instead. With piped input it lints stdin and reports file:null, exit 0 (checked: run(\['lint','--file',''\], stdin 'Lorem ipsum') returns 1 finding). A repeated --file or --rules quietly overwrites the earlier value. The Input reading rule says both must exit 1. — fix: In parse(), refuse v === '' and refuse a flag already in flags with KitExit(..., 1). Add tests for both.
- **JSON finding lines are wrong for strings with \n or other escapes** — `src/lib/kit/sample-content.js:198` (correctness): The line is computed as base + f.line - 1, where f.line counts real newlines in the decoded string. In the raw JSON those newlines are '\n' escapes on one line, so the line is pushed past the string. Checked: a lorem in the third segment of the string on line 2 is reported at line 4. Line 195 also searches for JSON.stringify(v) in the raw text, so a string written with different escapes (for example \u00e9 or \/) is not found and its findings fall back to line 1. Body copy stored in JSON often has \n and escapes. — fix: Report the line where the string starts (base) for every finding in it, or map offsets through the raw escaped text. Find the string's position from the parse position instead of re-stringifying. Add a test with a multi-line string and a \u escape.

## Low (1)

- **round-figure flags status codes and ordinary counts in realistic copy** — `src/lib/kit/sample-content.js:137` (correctness): Every multiple of 100 that is 100 or more is flagged, with no context check. 'Error 500: server down. Please retry.' and 'Returns 200 OK' each give a round-figure finding, and so do normal pricing and plan copy like '$300 a month for up to 500 seats' and '1,200 reviewers'. This matches the contract's wording but cries wolf on real marketing and error copy, so people will learn to ignore the advisory output. — fix: Skip numbers right after words like error, status, HTTP or code, and numbers followed by OK, so 'Error 500' and '200 OK' are not flagged. Consider flagging only 1,000 or more, or only numbers next to claim words such as users, customers or teams, when they are not prices.
