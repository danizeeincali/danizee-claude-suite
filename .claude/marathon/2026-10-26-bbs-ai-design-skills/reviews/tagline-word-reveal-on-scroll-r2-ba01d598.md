## Medium (3)

- **Easing check lets through input that breaks the style block and leaves words dimmed for good** — `src/lib/kit/word-reveal.js:57` (correctness): normalizeOptions only refuses ; { } \< \> and control characters. Confirmed by running it: emit accepts --easing 'ease"', 'ease /\*', 'cubic-bezier(0.2' and 'ease\\', and writes each one straight into \`transition:opacity 500ms \<easing\>}\`. In CSS, an unclosed string, an unclosed comment, an unclosed function or a trailing backslash each swallows the closing } and the rules after it. The \`.wr-js .wr-w.wr-on{opacity:1}\` rule and the prefers-reduced-motion override are lost. The script still adds wr-js, so every word stays at the muted opacity forever, including for reduced-motion users. The command exits 0 with no warning. — fix: Allow only a whitelist: a CSS keyword (ease, linear, ease-in, ease-out, ease-in-out, step-start, step-end), or cubic-bezier(n,n,n,n) / steps(n\[, keyword\]) / linear(...) made of numbers, percentages, commas and spaces with balanced parentheses. Refuse anything else with exit 1, and add tests for a quote, /\*, an unbalanced ( and a backslash.
- **Each fragment's script takes over every tagline on the page** — `src/lib/kit/word-reveal.js:88` (correctness): The emitted script selects document.querySelectorAll("\[data-word-reveal\]"). It does not select only its own \<p\>. With two emitted taglines on one page, the second script also adds wr-js to the first block and observes it, using the second block's STAGGER and MARGIN. Two observers then race on the first block, so it reveals at whichever trigger line comes first, possibly with the other block's stagger. The --trigger and --stagger-ms options given for the first tagline are silently overridden. A second fragment emitted with defaults also re-runs seq on blocks that are already revealed. — fix: Scope the script to its own fragment: use document.currentScript.previousElementSibling (past the \<style\>) or a unique data id emitted per fragment, and observe only that element. Add a harness test with two roots and different options.
- **Lint reports a handler throttled at its definition, the most common pattern** — `src/lib/kit/word-reveal.js:100` (correctness): A named handler counts only if defRe finds a function or arrow body and that body contains the call. \`const onScroll = throttle(update, 100); addEventListener('scroll', onScroll)\` has no body, so it is not in defs and is flagged. \`const onScroll = debounce(() =\> { update(); }, 100)\` is matched at the inner arrow body, which starts after the debounce( call, so it is flagged too. Both were confirmed by running them: each gives a finding on line 2. The inline form \`addEventListener('scroll', throttle(go, 100))\` passes, so the advisory gives a false positive exactly where the code follows its own advice. — fix: Also record \`(const|let|var) name = \<throttle|debounce|requestAnimationFrame...\>(\` in defs as throttled, or check for a call between the start of the definition and the end of its initializer, not only inside the body. Add tests for both named forms.

## Low (2)

- **Lint string scanner is thrown off by apostrophes in HTML text** — `src/lib/kit/word-reveal.js:63` (correctness): blank() treats every ' " or \` as the start of a JS string, even in HTML text outside \<script\>. It also does not handle regex literals, HTML \<!-- --\> comments, or ${} inside a template. In a minified page such as \`\<p\>Don't\</p\>\<script\>addEventListener('scroll',()=\>requestAnimationFrame(f))\</script\>\` (confirmed by running it), the string state flips, the requestAnimationFrame call is blanked, and the throttled listener is reported. A listener inside an HTML comment is also reported. The lint is advisory, so this produces a false finding but breaks nothing. — fix: For HTML input, lint only the contents of \<script\> elements (and drop \<!-- --\> comments) before running blank(). Add a one-line minified-HTML test.
- **stagger-ms has no upper bound, so a large value turns the reveal into a near-instant one** — `src/lib/kit/word-reveal.js:38` (correctness): staggerMs only has to be 0 or more. Browsers clamp a setTimeout delay above 2^31-1 ms to almost zero. With --stagger-ms 1e9, every word from the third on (i\*STAGGER over about 2.1e9) fires at once, ahead of the second word, so the reading-order reveal is broken. No message warns about it. — fix: Refuse stagger-ms above a sane cap (for example 10000) with exit 1, or above (2^31-1)/MAX\_WORDS.
