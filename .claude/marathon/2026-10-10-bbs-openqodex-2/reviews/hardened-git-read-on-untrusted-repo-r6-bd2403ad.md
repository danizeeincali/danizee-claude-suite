## Medium (1)

- **Driver discovery opens any path the repo's core.attributesFile names, and follows symlinked attribute files, though git in the shadow never reads them** — `src/lib/kit/safe-git.js:530` (security): overridesFor takes core.attributesfile from the untrusted repo config and calls readCapped(path.resolve(base, value)). readCapped uses fs.stat and readFile, so it follows symlinks and accepts any absolute path. It does the same for gitDir/info/attributes, even when info/ is a symlink (buildShadow skips a symlinked info/ but this read does not), and for every work-tree .gitattributes, which git \>= 2.32 does not follow when it is a symlink. Traced on git 2.43: repo h with \`core.attributesFile=\<scratch\>/outside/attrs\` (a file outside the repo holding \`\* filter=fromoutside\`). \`strace\` of \`cli.js safe-git --dir h -- rev-parse HEAD\` shows statx and openat of outside/attrs, and safeGitConfig(h) returns filter.fromoutside.\* overrides, so the wrapper read a file outside the repository that the attacker chose. On Windows a value like \`//attacker/share/x\` makes the wrapper open an SMB connection with the user's NTLM credentials. Round 4 removed include.path reading for exactly this reason ('a UNC share that sends the user's credentials'). The shadow never sets core.attributesFile, and git does not follow symlinked .gitattributes, so none of these reads is needed for safety. — fix: Drop core.attributesFile discovery, since the shadow config never sets it. Otherwise only accept a value that resolves inside commonDir/gitDir/top, refused when absolute or UNC. Read every attribute file with lstat + O\_NOFOLLOW, as copyCapped does, and skip symlinks. Add a test with core.attributesFile pointing at an outside file and assert it is never opened.

## Low (4)

- **'Nothing is cached' / 'there is no cache any more' is untrue: the git path is cached per PATH for the process lifetime** — `src/lib/kit/safe-git.js:82` (facts): The header says nothing is cached, and the comment on clearSafeGitCache (line 470) says there is no cache. resolveGit keeps gitPathCache, keyed by the PATH string, and clearSafeGitCache does not clear it. In a long-running process, if the git it found is removed or moved (an upgrade that relocates /usr/local/bin/git), every later call fails with 'cannot run git: spawnSync ... ENOENT' even though PATH has another git, and clearSafeGitCache() does not help. The test at test/kit-hardened-git-read-on-untrusted-repo.test.js:460 is still named 'invalidates the cache' although there is no config cache to invalidate. — fix: Make clearSafeGitCache clear gitPathCache, or drop the cache. Change the header to 'repository state is never cached'. Rename the test to '... is seen by the next call'.
- **Implicit no-index happens when EITHER path is outside the work tree, not 'both'** — `src/lib/kit/safe-git.js:73` (facts): The header (line 73) and the comment at line 764 say git diff goes no-index on its own 'when both paths lie outside the work tree'. git's condition is that at least one path is outside. Traced on git 2.43: in repo r, \`git diff a.txt \<abs\>/out.txt\` printed the diff of a.txt against the outside file, with '+secret'. The code is safe because it refuses each escaping argument. But the stated rule invites someone to relax the check to 'refuse only when both are outside', which would reopen the outside-file read. — fix: Say 'when either path lies outside the work tree' in both places.
- **Exact, harmless options (diff --text, rev-list --filter=...) are refused with a message claiming they re-enable code execution** — `src/lib/kit/safe-git.js:755` (facts): The prefix rule refuses any long option that is a prefix of a denied option, including real options that git matches exactly before it tries abbreviations. \`safe-git --dir h -- diff --text\` exits 2 with 'git option --text would re-enable code execution, write a file or read a submodule', but --text is -a (treat as text), not --textconv. \`rev-list --filter=blob:none --objects HEAD\` is refused the same way, but rev-list's --filter is an object filter, not cat-file's --filters. The refusal text states something false about these options. The test at line 508 claims ordinary long options keep working, and it does not cover them. — fix: Exempt exact option names that the subcommand really has (at least 'text' for the diffing commands and 'filter' for rev-list/log) from the prefix rule, or word the message as 'is, or abbreviates, a denied option'.
- **'then behaviour is unchanged' / 'existing behaviour' are untrue: the kit-missing path now runs a different command** — `src/lib/bbs/fetch.js:411` (docs): loadSafeGit's comment says that when the kit is missing 'behaviour is unchanged'. The test at test/kit-hardened-git-read-on-untrusted-repo.test.js:349 is named 'keeps the plain call (existing behaviour)'. Both are wrong after round 5: the fallback now runs \`git --git-dir \<dest\>/.git rev-parse HEAD\` from the clone's parent folder, with git resolved to an absolute path, and the test asserts exactly that new argv. A reader auditing the bbs-without-kit install is told nothing changed there. — fix: Reword to 'falls back to the plain runner (absolute git, --git-dir, cwd outside the clone)' and rename the test accordingly.
