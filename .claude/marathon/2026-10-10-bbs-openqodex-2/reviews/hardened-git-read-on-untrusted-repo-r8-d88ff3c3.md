## Medium (2)

- **The caller's git command runs with no timeout when none is passed (CLI always), so a FIFO .gitattributes hangs safe-git forever** — `src/lib/kit/safe-git.js:600` (correctness): makeCtx sets ctx.timeout = timeout ?? INTERNAL\_TIMEOUT, but safeGit calls exec(argv, { input, timeout }) and raw() builds { ..., timeout: ctx.timeout, ...extra }. The explicit \`timeout: undefined\` in extra overwrites the default, so the user's command (and describeDirty's three calls) run with spawnSync timeout undefined. The CLI never passes a timeout. I traced it on git 2.43 with a repo that has a commit, a modified a.txt, and \`mkfifo .gitattributes\` in the work tree. \`cli.js safe-git --dir \<repo\> -- diff HEAD\` blocks forever (killed by \`timeout 20\`, exit 124). A spy runner shows the four internal calls finish with timeout=60000 and the final \`diff ... HEAD\` gets timeout=undefined. git opens the FIFO with O\_RDONLY to look up the diff driver and waits for a writer. With { timeout: 3000 } the same call ends with KitExit 1 (ETIMEDOUT). safe-git itself avoids FIFOs (O\_NONBLOCK reads, --no-includes 'a FIFO that hangs the read'), but the git it starts does not, and a repo unpacked from an archive can carry a FIFO. The bbs caller passes timeoutMs, so it is not affected. — fix: Fill in the default before spreading: in safeGit/describeDirty pass \`timeout: ctx.timeout\` (or in raw use \`timeout: extra.timeout ?? ctx.timeout\`). Add a test with a FIFO .gitattributes and an injected short default, checking that the CLI path returns a timeout error.
- **CLI drops piped stdin: \`--stdin\` / \`--batch\*\` commands return empty output with exit 0** — `src/lib/kit/safe-git.js:929` (correctness): cli.js hands every verb io.stdin and io.stdinIsTTY, but safe-git's run() never reads them and calls safeGit without \`input\`, so git's stdin is closed. I traced \`echo HEAD | cli.js safe-git --dir r -- cat-file --batch-check\` and \`echo HEAD | cli.js safe-git --dir r -- rev-list --stdin\` against a repo with one commit. Both print {stdout:'', code:0, exit:0}, which reads as 'no such object' or 'no commits' instead of an error. The library API supports \`input\`, the allow-list admits these stdin-reading options (cat-file --batch/--batch-check/--batch-command, rev-list/log/diff-tree --stdin, name-rev --annotate-stdin), and the usage text never says the CLI cannot take stdin. — fix: In run(), when !io.stdinIsTTY and the git args use a stdin-reading option, pass \`input: await io.stdin()\` to safeGit. Read stdin only in that case, so an open pipe does not block other commands. Otherwise refuse those options in the CLI with a message (KitExit 1). Add a CLI test that pipes HEAD into cat-file --batch-check.

## Low (1)

- **A \`limits\` key set to undefined replaces the default: entries cap silently off, file caps crash with RangeError** — `src/lib/kit/safe-git.js:589` (correctness): makeCtx and buildShadow merge with { ...DEFAULT\_LIMITS, ...limits }, so a caller passing { limits: { index: opts.maxIndex } } with maxIndex unset overrides the default with undefined. Traced: safeGit(repo, \['rev-parse','HEAD'\], { limits: { index: undefined } }) and { total: undefined } both throw a raw RangeError ERR\_OUT\_OF\_RANGE (Buffer.alloc(NaN) in copyCapped) instead of a KitExit. { entries: undefined } turns off the refs/ walk cap entirely (\`++entries \> undefined\` is never true). Neither happens through the CLI or the bbs caller, which pass no limits. — fix: Merge only defined, finite, non-negative numbers (e.g. filter Object.entries(limits) by Number.isFinite(v) && v \>= 0), or throw KitExit 1 for an invalid limit.
