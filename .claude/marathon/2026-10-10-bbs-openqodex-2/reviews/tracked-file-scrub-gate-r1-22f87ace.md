## Medium (3)

- **A tracked private pattern file is skipped, so the gate passes while publishing the private patterns** — `src/lib/kit/scrub.js:48` (security): EXCLUDED always drops .claude/kit/scrub-patterns.local from the scan, even when it is tracked in HEAD. That happens after \`git add -f\`, or in a repo whose .gitignore lacks the kit rule. In that case the push would publish the private strings themselves, yet scrub reports clean. Reproduced: with the .local file force-committed, \`scrub\` returns exit 0 and clean:true, and push-gate check would then abstain. The private file exists so that these strings stay out of the remote, so this is the one leak the gate should never miss. (The same applies, less critically, to .claude/helpers/kit/scrub.js and src/lib/kit/scrub.js, which are excluded by path in every repository.) — fix: When PRIVATE\_FILE appears in the listed tracked files, treat it as a hit or a refusal (for example, 'the private pattern file is tracked and would be pushed') instead of silently excluding it. Keep the exclusion only for content matching.
- **A UTF-16 pattern file is read as UTF-8, so every pattern silently never matches** — `src/lib/kit/scrub.js:93` (correctness): readPatternFile always decodes as UTF-8, and parsePatterns strips only a U+FEFF character. A pattern file written as UTF-16LE with a BOM (what Windows PowerShell 5's \`\>\`/Out-File produces) parses into valid regexes full of NULs and U+FFFD. These never match normal text. Reproduced: .local file = FF FE + 'zebra-secret\r\n' in UTF-16LE, and a committed a.txt containing zebra-secret. Result: scrub exits 0 with clean:true and 0 hits, and push-gate check is not blocked. The scanned files get BOM-aware decoding (decodeText), but the pattern input does not, so the configured gate is quietly not enforced. — fix: Read the pattern file as a Buffer and decode it with decodeText(). Also refuse (exit 1) a pattern file that still contains NUL after decoding.
- **--worktree allocates and zero-fills a cap-sized buffer for every file** — `src/lib/kit/scrub.js:208` (performance): readBounded does Buffer.alloc(cap + 1) for each file regardless of its size, so the default is 32 MiB zero-filled per file. Measured on 3000 six-byte tracked files: HEAD mode took 285 ms and --worktree took 7475 ms (about 26x slower). The cost grows linearly with file count and with --max-file-bytes. A raised cap such as 1e11 makes every allocation throw, which is the low finding below. — fix: Allocate Math.min(st.size, cap) + 1 (the lstat size is already known) and grow only if the file turns out longer, or read into a small reused chunk buffer while counting toward cap.

## Low (2)

- **A large --max-file-bytes makes every worktree file 'cannot read: error'** — `src/lib/kit/scrub.js:282` (correctness): --max-file-bytes accepts up to 16 digits (line 384), but readBounded's Buffer.alloc(cap + 1) throws a RangeError above the buffer limit. That error is caught per file, so \`scrub --worktree --max-file-bytes 100000000000\` lists every file as not\_scanned with reason 'cannot read: error'. The run fails closed (exit 2), but the reason points nowhere near the flag. — fix: Cap --max-file-bytes at buffer.constants.MAX\_LENGTH (or a documented maximum) in parseArgs with an exit-1 message, and/or stop allocating cap-sized buffers.
- **--worktree reports non-UTF-8 file names as 'tracked but missing on disk'** — `src/lib/kit/scrub.js:241` (correctness): ls-files -z output is decoded as UTF-8, so a tracked path containing a non-UTF-8 byte (for example 'bad\xe9.txt') becomes 'bad\uFFFD.txt'. fs.lstat then gets ENOENT. Reproduced: HEAD mode reports the hit in that file, but --worktree reports 0 hits plus not\_scanned 'tracked but missing on disk' for a file that is present. It fails closed (exit 2), but --worktree can never pass in such a repository, and the reason is wrong. — fix: Run ls-files through the latin1 binaryRunner path and build the on-disk path from the raw bytes (Buffer.from(p, 'latin1')), keeping a UTF-8 rendering only for display.
