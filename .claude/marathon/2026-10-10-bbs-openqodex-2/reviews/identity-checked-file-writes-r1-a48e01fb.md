## High (1)

- **guarded-write with no piped stdin silently truncates the target to 0 bytes** — `src/lib/kit/guarded-fs.js:305` (correctness): run() writes whatever io.stdin() returns. cli.js readStdin returns '' when stdin is a TTY, and an empty stdin (\</dev/null, or a harness that closes stdin) also gives ''. guardedWrite then atomically replaces an existing file with an empty one and exits 0 with written:true. Reproduced: \`echo important \> home/rc; kit guarded-write --root home --file home/rc \</dev/null\` leaves rc at 0 bytes; the same under a pseudo-TTY (script -qc) creates a 0-byte file without waiting for input. Running the verb interactively, without a pipe, destroys the file's contents. The same code is in .claude/helpers/kit/guarded-fs.js:305. — fix: In run(), refuse with exit 1 when io.stdinIsTTY is true. Also refuse empty content unless an explicit flag such as --allow-empty is given.

## Medium (3)

- **CLI stdin is decoded as UTF-8, so binary or non-UTF-8 content is corrupted** — `src/lib/kit/guarded-fs.js:305` (correctness): cli.js readStdin returns Buffer.concat(chunks).toString('utf-8'), and run() passes that string to guardedWrite, which re-encodes it as UTF-8. Invalid bytes become U+FFFD. Reproduced: piping bytes ff fe 00 80 produced a 10-byte file (ef bf bd ef bf bd 00 ef bf bd), and the result still reported written:true. guardedWrite accepts a Buffer, but the stdin input path cannot deliver one. — fix: Have the CLI pass the raw Buffer for guarded-write (for example an io.stdinBuffer(), or readStdin({ raw: true })) and hand it to guardedWrite unchanged.
- **Off Linux, a parent folder swapped after openParent sends the rename outside root, and the rollback then deletes the clobbered outside file** — `src/lib/kit/guarded-fs.js:165` (security): When PROC is false (macOS and other non-Linux systems), base is the path res.parent, not the opened handle. If the folder is swapped for a link after openParent (the afterOpen window), the temp file is created and renamed through that link, replacing any same-named file outside root. The post-rename lstat goes through the same link, so the identity check passes. recheck() then refuses, and the rollback unlinks finalVia, which deletes the outside file. Reproduced with a copy of the module where PROC=false: outside/x containing 'PRECIOUS' was gone after guardedWrite threw KitExit 2. The header says a folder swapped after the walk is refused and nothing is written there, but off Linux a file outside the root is destroyed. — fix: Off Linux, after creating the temp file and again just before rename, fstat the directory handle and compare it with lstat of the path; abort on any mismatch. Do not unlink in the rollback unless the parent path still resolves to the opened folder's dev+ino. If neither is possible, refuse to run when PROC is false.
- **push-gate header claims a walk from the home folder, confined to home, but the root is the receipts folder's real parent** — `src/lib/kit/push-gate.js:17` (facts): The header says store access is an 'identity-checked walk from the home folder' and that 'a dotfile link above it is followed while it stays under home'. storeFile() actually realpaths the receipts folder's parent (~/.claude/kit) and uses it as root, so a ~/.claude link that points anywhere, including outside home, is accepted. The new test 'a ~/.claude that links outside the home folder still stores receipts' asserts exactly that. The comment in the packaged test ('HOME is the root', test/kit-identity-checked-file-writes-packaged.test.js:31) repeats the error. A reader would assume a confinement to home that does not exist. The same text is in .claude/helpers/kit/push-gate.js. — fix: Rewrite the header to say that links above the store are resolved without confinement, the root is the store's real parent, and only links inside the receipts folder are refused. Fix the packaged test comment to match.

## Low (2)

- **guarded-write silently resets an existing file's permissions to 0600** — `src/lib/kit/guarded-fs.js:172` (correctness): The temp file is created with mode 0600 (the default) and renamed over the target, so an existing file loses its original mode. Reproduced: a 0755 run.sh was 0600 after \`kit guarded-write\`, so its exec bit was gone. Neither the CLI usage nor the header mentions this. — fix: When the final name already exists as a regular file, create the temp file with that file's mode, or document the 0600 reset in the usage text.
- **Dotfile-link push-gate test ends with a meaningless assertion and does not check the refused write left nothing behind** — `test/kit-identity-checked-file-writes.test.js:215` (test-quality): assert.ok(f) only checks that a string is non-empty. After the refused receipt, the test never checks that receipts.real kept its original single JSON file and gained no temp or lock files, so a refusal that came after a partial write would still pass. — fix: Replace assert.ok(f) with assertions that receipts.real still holds only the original JSON file with unchanged content, and no .tmp or .lock leftovers.
