## Medium (1)

- **Index-path check applies Windows rules on POSIX: a repository with a file named 'a:b', 'x/..\..\f' or 'x/C:\\t' is refused outright, so bbs cannot fetch it** — `src/lib/kit/safe-git.js:507` (correctness): unsafeIndexPath treats a leading '\<letter\>:' as an absolute path and splits components on backslash on every platform. On Linux and macOS git treats these as ordinary file names: verify\_path rejects backslashes only on Windows, and clone checks them out as literal names. Nothing is read outside the work tree. Reproduced on git 2.43: a repo with a top-level file 'a:b' gives \`kit: refused: the index has an entry "a:b" (absolute path) that would make git read outside the work tree\` (exit 2), even for \`rev-parse HEAD\`. With that file removed, 'tests/fixtures/..\..\evil.txt' (a typical path-traversal test fixture) is refused as component "..", and 'tests/fixtures/C:\\temp.txt' as component "". checkIndexPaths runs before every command with a work tree, so the whole repository becomes unreadable. Through the bbs caller, cloneRepo then fails ('git rev-parse HEAD failed after clone') and deletes the clone. The refusal message is also untrue on POSIX. — fix: Split on '\\' and test /^\[A-Za-z\]:/ only when process.platform === 'win32', as git's verify\_path does. Keep the '/'-based '', '.', '..' and .git-alias checks everywhere, and add POSIX 'good' cases ('a:b', 'x\\..\\y') to the unit test.

## Low (5)

- **CLI crashes with a TypeError for a subcommand named like an Object.prototype key ('constructor', 'toString', '\_\_proto\_\_')** — `src/lib/kit/safe-git.js:140` (correctness): readsStdin indexes STDIN\_OPTIONS\[args\[0\]\] on the raw CLI argv before checkReadArgs runs. For 'constructor' it gets Object (a function) and spreads it, which throws. Reproduced: \`cli.js safe-git --dir R -- constructor --x\` prints \`kit: (STDIN\_OPTIONS\[args\[0\]\] || \[\]) is not iterable\` and exits 1, where every other unknown subcommand ('fetch --x') gets the documented exit-2 'not on the read-only allow-list' refusal. — fix: Use \`Object.hasOwn(STDIN\_OPTIONS, args\[0\]) ? STDIN\_OPTIONS\[args\[0\]\] : \[\]\`, or run checkReadArgs before readsStdin in run().
- **safeGitConfig JSDoc still says names from a .gitattributes listed by ls-files are included** — `src/lib/kit/safe-git.js:695` (docs): 656da9d stopped reading work-tree and index .gitattributes for driver names: overridesFor uses only config entries and info/attributes, and the tests now assert that such names are NOT listed. The exported function's doc still says overrides cover every driver named in 'info/attributes or a .gitattributes the shadow's ls-files lists'. A caller reading the API doc would expect a name used only in .gitattributes to appear in the result, and it does not. — fix: Drop 'or a .gitattributes the shadow's ls-files lists'. Say that work-tree and index .gitattributes are not read, because the shadow config defines no driver.
- **Packaged test's 'runs nothing' check for a .gitattributes-only name has no driver behind it and no plain-git control** — `test/kit-hardened-git-read-on-untrusted-repo-packaged.test.js:64` (test-quality): The rewritten packaged block appends '\*.txt filter=bad;name' to .gitattributes and then asserts that the markers folder is empty. No filter.bad;name driver is defined anywhere, and this line overrides the earlier 'filter=evil' for \*.txt. So plain git would run nothing for f.txt either, and the assertion would pass even if the installed safe-git did read that name and somehow defined it. The unit tests use hiddenDriver plus a plain-git control for this, but the end-to-end packaged path (.claude/helpers copy through the installed CLI) has no proof that a name only in a .gitattributes never runs. — fix: Define the driver through an include.path file (as hiddenDriver does) so that plain git runs it. Assert no marker through pkg.kit, then run plain git as the control and assert that the marker appears.
- **The repository's config file is read by two git spawns on every call** — `src/lib/kit/safe-git.js:567` (performance): inspect() calls readConfigFile(mainCfg) once for repoFormat and again in the \`for (const f of files)\` loop, because files starts with mainCfg. Counted with an injected runner: a plain \`safeGit(dir, \['rev-parse','HEAD'\])\` spawns \`git config --file .git/config --no-includes --list -z\` twice before ls-files and the command. On a hostile repo this doubles the time a large config costs. A sparse 2 GiB .git/config takes about 20 s per read on git 2.43, so about 40 s per call, and each read gets its own full timeout. Two reads can also see different contents, with fmt taken from the first and core from the second. — fix: Read the main config once, reuse its entries for repoFormat and as the first block of \`entries\`, and read only config.worktree in the loop.
- **checkIndexPaths doc says an output overflow is KitExit 1; it is exit 3 and the message tells the user to narrow a command they never ran** — `src/lib/kit/safe-git.js:520` (docs): defaultGitRunner turns ENOBUFS into KitExit(GIT\_FAILED\_EXIT = 3), 'git ls-files wrote more than 256 MiB of output; narrow the command'. When the internal \`ls-files -z --stage\` index listing overflows, the user, who asked for something like \`rev-parse HEAD\`, gets exit 3 ('git ran and failed' per the usage) and advice to narrow an ls-files they did not run. The doc comment claims 'KitExit 1, fail closed'. This can happen with a version-4 (prefix-compressed) index under the 256 MiB copy cap that expands to more than 256 MiB of listing. — fix: In checkIndexPaths, catch the overflow and rethrow KitExit 1 (or 2) saying that the index listing is too large to check, or correct the comment.
