## Medium (1)

- **Alternates refusal is bypassed by a symlinked objects/ or objects/pack: safe-git serves another repository's objects** — `src/lib/kit/safe-git.js:606` (security): Round 10 refused objects/info/alternates because it 'serves other repositories' objects', but the same effect needs no alternates file. GIT\_OBJECT\_DIRECTORY is \<commonDir\>/objects (line 684); finishLocate only checks isDir (it follows symlinks), and nothing checks objects/ or objects/pack. Traced on git 2.43 with the CLI. (1) evil1/.git/objects -\> /abs/secret/.git/objects. \`safe-git --dir evil1 --input - -- cat-file --batch-all-objects --batch \</dev/null\` printed TOPSECRET\_MARKER, the blob of a different repository on disk. --batch-all-objects needs no SHA. (2) evil2/.git/objects/pack -\> /abs/secret/.git/objects/pack, with the repo's own loose objects still in place: the same command printed TOPSECRET\_MARKER. A tarball or shared-folder copy of a repo carries symlinks just as it carries the alternates file that round 10 refused. safe-git already refuses a symlinked refs/ for this reason (copyTree), but not a symlinked objects/. Related: a .git symlink, or a \`gitdir: ../secret/.git\` file, opens the other repository outright (both traced: TOPSECRET\_MARKER printed). Linked worktrees legitimately use gitdir:, so that case at least deserves a documented caveat. — fix: In checkNoAlternates or finishLocate, lstat \<commonDir\>/objects and objects/pack (and objects/info) and refuse (KitExit 2) when one is a symlink, or when realpath(objects) is not inside commonDir. Add tests for both symlink layouts that use a marker blob, and list the remaining gitdir:/.git-symlink exposure in the header.

## Low (3)

- **The UTF-8 'fail closed' check on index-only .gitattributes can be steered so that a trailing driver is silently dropped** — `src/lib/kit/safe-git.js:513` (correctness): Each invalid byte decodes to U+FFFD (3 bytes), so with k invalid bytes buf\[nl+1+size\] lands on original byte size-2k. A blob with a '\n' at that offset passes the check, and its last 2k bytes are cut off without any error. Traced: a committed .gitattributes of 7 bytes 0xff + '# x\n\* filter=evil' (no trailing newline), then deleted from the work tree. \`git check-attr filter a.txt\` reports 'evil', but safeGitConfig's overrides contain no filter.evil.\* entries. The control case with ASCII bytes in place of 0xff does list filter.ctl.\*. With no config able to define the driver nothing runs, but the code comment's 'fail closed rather than parse a shifted stream' guarantee does not hold. — fix: Have the runner return stdout as a Buffer for this call (encoding 'buffer'/latin1), or read blobs with \`cat-file --batch\` and parse them by byte length before decoding. Alternatively, refuse when the decoded text contains U+FFFD. Add the 0xff test.
- **Index-only .gitattributes lookup asks for stage 0 only; git reads stage 2 of an unmerged file** — `src/lib/kit/safe-git.js:490` (correctness): For a .gitattributes that is missing from the work tree, the code queries \`:rel\`, which is stage 0. During a conflicted merge the index holds only stages 1/2/3, and git's read\_blob\_data\_from\_index falls back to stage 2 ('ours'). Traced: the .gitattributes conflicted (stage 2 '\* filter=ours2', stage 3 '\* filter=theirs3'), then removed from the work tree. \`git check-attr filter a.txt\` gives 'ours2', while safeGitConfig lists neither driver: batch-check answered 'missing' and the file was skipped. This is a defence-in-depth gap only, since no config can define the driver. — fix: When \`:rel\` is missing, also query \`:2:rel\` (or take the blob ids and stages straight from the \`ls-files --stage\` output already produced by checkIndexPaths).
- **Round-9 fix incomplete: \`cat-file --batch-all-objects --batch\` is still refused without --input -** — `src/lib/kit/safe-git.js:123` (correctness): readsStdin exempts 'batch' and 'batch-check' when --batch-all-objects is present, but it tests every STDIN\_LONG entry with startsWith. 'batch-command'.startsWith('batch') is true, so a plain \`--batch\` still counts as reading stdin. git matches the exact option --batch first, and with --batch-all-objects it reads no stdin. Traced from a TTY: \`safe-git --dir repo -- cat-file --batch-all-objects --batch\` exits 1 with 'reads stdin: pass --input -', while plain git prints every object. The test at test/...test.js:1669 covers only --batch-check. — fix: Treat an exact option name as itself before the prefix match: if STDIN\_LONG includes name, judge only that entry, and use the prefix match only for abbreviations. Add \`--batch-all-objects --batch\` to the TTY test.
