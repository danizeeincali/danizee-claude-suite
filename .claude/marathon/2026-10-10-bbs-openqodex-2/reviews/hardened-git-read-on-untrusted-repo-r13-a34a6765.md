## Medium (1)

- **Header says another repository is reached only through a .git file or commondir, but a symlinked .git silently reads another repository** — `src/lib/kit/safe-git.js:28` (facts): Lines 26-30 refuse a symlinked objects/ or any symlink under it because it 'would read another repository's objects', and then name a .git file (gitdir:) or commondir as the one documented way to reach another repository. locateRepo (line 302) stats .git with fs.stat, which follows symlinks, and finishLocate realpaths it, so a .git that is a symlink to another repository is accepted with no refusal and no caveat. Traced on git 2.43: secret/ is a repo with a commit 'SECRETMSG'; evil/.git -\> /abs/secret/.git; \`node src/lib/kit/cli.js safe-git --dir evil -- log --oneline\` exits 0 and prints '5999f31 SECRETMSG'. This is the same effect the objects/ symlink refusal exists to stop. A tarball or shared-folder copy can carry it as easily as the symlinked objects/ that round 11 reported, and round 11's detail already called out this exact case as needing a documented caveat. A reader of the header (and of the usage) is told that symlinks leading to other repositories are refused, and that the only exception is gitdir:/commondir. — fix: Either refuse a .git that is a symlink (lstat it in locateRepo, as refs/ and objects/ are handled), or add it to the documented exception next to the gitdir:/commondir sentence, and add a test for whichever behaviour is chosen.
