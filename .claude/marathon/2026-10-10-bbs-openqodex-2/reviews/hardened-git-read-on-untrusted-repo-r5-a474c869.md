## Medium (2)

- **Kit-missing fallback still spawns bare 'git' with cwd inside the fresh clone, so a git committed to the repo runs** — `src/lib/bbs/fetch.js:385` (security): bbs and kit are separate plugins (src/plugins/bbs.js and src/plugins/kit.js install helpers/bbs and helpers/kit independently), so bbs without kit is a supported install, and loadSafeGit() then returns null. headOf then calls runGit -\> execFileSync('git', \['rev-parse','HEAD'\], { cwd: dest }). The name 'git' is looked up through an empty or '.' PATH entry on POSIX, and in the cwd first on Windows (libuv search\_path). cloneEnv keeps PATH as it is. I proved it with a repo whose root holds a committed 0755 file named 'git' that touches a marker and then execs /usr/bin/git. headOf(repo, {PATH:':/usr/bin:/bin'}, { load: async () =\> null }) created markers/repo-git-ran. The same call through the kit path (default load) created no marker. This is the hole round 4 fixed in safe-git (resolveGit), left open on the one path that touches a just-cloned foreign checkout. — fix: In runGit, spawn git by an absolute path found only in the absolute PATH entries (reuse the resolveGit logic, or copy it into bbs so it works without the kit), and/or run the fallback rev-parse with cwd outside dest using --git-dir=\<dest\>/.git.
- **A subfolder --dir silently re-roots pathspecs to the top; usage text never says so** — `src/lib/kit/safe-git.js:87` (accessibility): Every command runs as if from the top of the work tree. Only the module header comment says this; the usage string a CLI user sees does not. With repo r holding sub/f, \`safe-git --dir r/sub -- log --oneline -- f\` returns {stdout:'', code:0}: an empty history with a success code for a file that has history. In git, \`cd r/sub && git log -- f\` shows the commit. \`ls-files\` from r/sub prints 'sub/f' (top-relative), and \`show HEAD:./f\` fails with git's own 'relative path syntax can't be used outside working tree', which says nothing about safe-git. Someone pointing --dir at a subfolder gets a wrong, silent answer and nothing tells them why. — fix: State in \`usage\` that paths are relative to the repository top whatever --dir names. Also report the prefix: add a \`prefix\` field to the result, or a stderr note when loc.real is below top and the argv has pathspecs. Alternatively, refuse a relative pathspec after '--' when --dir is a subfolder.

A shell caller using \`kit safe-git ... && next\` or \`set -e\` treats a failed git read as success. The usage does say that { code } is printed, so this is drift, not hidden behaviour. — fix: In run(), return { ...result, exit: result.code === 0 ? 0 : 1 } (the code is still in the JSON), or document in the usage that the exit status is 0 whenever git ran.

No program runs, because --no-ext-diff and --no-textconv are still inserted. The documented deny list still misstates what the wrapper allows. — fix: For diff, refuse when the two non-option arguments are paths outside the work tree (or any absolute path argument), or correct the header to say the implicit no-index form is allowed.
