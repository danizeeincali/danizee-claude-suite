## Medium (1)

- **The stdin guard misses name-rev --annotate-stdin and show-ref --exclude-existing, so both still return empty output with exit 0** — `src/lib/kit/safe-git.js:949` (correctness): The round-8 fix refuses a command without --input - only when an argument is exactly --stdin or starts with --batch. Two allow-listed commands read stdin under other option names: \`name-rev --annotate-stdin\` (and git's accepted abbreviation \`--annotate\`) and \`show-ref --exclude-existing\[=pattern\]\`. Traced on git 2.43 with a repo that has branch feat: \`echo \<HEAD sha\> | git name-rev --annotate-stdin\` prints '\<sha\> (feat)', and \`printf 'refs/heads/feat\nrefs/heads/nope\n' | git show-ref --exclude-existing\` prints 'refs/heads/nope'. Through \`cli.js safe-git --dir r -- name-rev --annotate-stdin\` and \`... -- show-ref --exclude-existing\`, both print {stdout:'', code:0, exit:0}. This is the same silent wrong answer round 8 reported for --stdin and --batch: 'no names' or 'every ref exists'. — fix: Match the stdin readers per subcommand and include prefixes: name-rev with a prefix of annotate-stdin (at least 'annotate') or stdin, show-ref with --exclude-existing\[=...\], plus the existing --stdin and --batch\* forms. Add a CLI test for each.

## Low (4)

- **cat-file --batch-all-objects needs no stdin, but can't be run from a terminal** — `src/lib/kit/safe-git.js:949` (correctness): \`/^--batch/\` also matches --batch-all-objects, which lists the object store and reads no stdin. From an interactive shell, \`safe-git --dir r -- cat-file --batch-check --batch-all-objects\` is refused with 'reads stdin: pass --input -'. Adding \`--input -\` is then refused with '--input - needs piped stdin, not a terminal' (traced with script(1)). The command only works with \`--input - \</dev/null\`, which neither message suggests. — fix: Exempt --batch-all-objects from the stdin rule. For example, require --input only for --batch\* when --batch-all-objects is absent.
- **timeout is not validated: 0 silently turns off the hang guard, and other bad values throw a raw RangeError** — `src/lib/kit/safe-git.js:589` (correctness): Round 8 validated \`limits\` (mergeLimits), but \`timeout\` still goes straight to spawnSync through \`timeout ?? INTERNAL\_TIMEOUT\`. Traced with safeGit(r, \['rev-parse','HEAD'\], { timeout }): with 0 the call succeeds with no time limit, so the FIFO .gitattributes hang fixed in round 8 comes back. With -1, '5000', Infinity, NaN or 1.5, it throws RangeError ERR\_OUT\_OF\_RANGE instead of a KitExit. bbs headOf forwards cloneRepo's timeoutMs unchanged. — fix: Validate timeout in makeCtx the same way as limits: undefined keeps INTERNAL\_TIMEOUT; anything else must be a positive safe integer, or KitExit 1.
- **The 60 s cap on the user's command is undocumented and reported as 'cannot run git ... ETIMEDOUT' (exit 1)** — `src/lib/kit/safe-git.js:209` (docs): Since 2a0a9e8, every git child, including the user's own command, is killed after INTERNAL\_TIMEOUT (60 s), and the CLI cannot raise it. Neither the header nor the usage mentions the cap. When it fires, the CLI prints 'kit: cannot run git: spawnSync /usr/bin/git ETIMEDOUT' and exits 1, which the usage defines as 'bad input'. Traced with a FIFO .gitattributes: exit 1 after 60.1 s. A legitimately slow read such as \`log -S\<string\>\` on a long history hits the same message. An output over the 256 MiB maxBuffer gives the equally opaque '... ENOBUFS'. — fix: Map ETIMEDOUT and ENOBUFS to clear messages ('git took longer than 60 s, killed' / 'git output over 256 MiB'), and state both caps in the header and usage. Optionally add a --timeout CLI flag.
