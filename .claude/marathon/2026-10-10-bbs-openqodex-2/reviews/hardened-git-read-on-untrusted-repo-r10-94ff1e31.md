## Medium (2)

- **The repo's objects/info/alternates is followed to any path: git opens files outside the repo (FIFOs, UNC shares) and serves other repositories' objects** — `src/lib/kit/safe-git.js:626` (security): GIT\_OBJECT\_DIRECTORY points at the untrusted repo's real objects/, so git reads its objects/info/alternates and follows every entry it lists, plus each alternate's own info/alternates, recursively. That is the same 'repo names any path' exposure the header says safe-git closed for include.path ('a FIFO or a UNC share it names is never touched'). Traced on git 2.43: (1) victim/.git/objects/info/alternates = /abs/outside/objects, whose info/alternates is a FIFO with a writer that touches a marker once the FIFO is opened. \`safe-git --dir victim -- log --oneline\` opened it and MARKER\_opened\_outside was created. (2) evil/.git/objects/info/alternates = /abs/secret/.git/objects. \`safe-git --dir evil -- cat-file -p \<blob sha\>\` printed TOPSECRET\_MARKER from a different repository on the user's disk. On Windows an entry such as \\attacker\share\objects makes git connect over SMB and send the user's NTLM credentials. On a degraded network the same entry, or an NFS path, stalls every call until the timeout. The same class reaches safe-git's own discovery code: a .git file's gitdir: and a commondir file are lstat'ed/realpath'ed wherever they point (line 277, line 292). A tarball or shared-folder copy of a repo carries objects/info/alternates; a clone does not. — fix: Before running git, read \<commonDir\>/objects/info/alternates as data (lstat to check it is a regular file, then a bounded read) and refuse (KitExit 2) when it lists any entry that is absolute, a UNC or drive path, or resolves outside commonDir. Alternatively, run git against a shadow objects dir whose info/ has no alternates. Apply the same inside-the-repo or not-UNC check to the gitdir: and commondir targets. Add a test using the FIFO and marker shown here.
- **Two git spawns per missing .gitattributes, each reloading the index: a repo with deleted attribute files takes minutes, and --timeout does not bound it** — `src/lib/kit/safe-git.js:473` (performance): workTreeAttributes runs \`cat-file -s :rel\` and then \`cat-file blob :rel\` as separate git processes for each tracked .gitattributes that is absent from the work tree. Each process re-reads the whole index, so the total time grows faster than the number of files. --timeout and the default 60000 ms apply to each child, not to the call, so the header's promise that 'a hostile repo cannot hang a read' does not hold. Measured: 1500 .gitattributes outside a sparse-checkout cone made \`safe-git -- rev-parse HEAD\` take 10.9 s (plain git: 0.002 s). 6000 deleted .gitattributes took 58.7 s, even with \`--timeout 5000\`. A hostile on-disk repo with tens of thousands of deleted .gitattributes stalls each call for many minutes. On older machines and on Windows, where a process spawn costs 30-50 ms, ordinary sparse monorepo checkouts become very slow too. — fix: Take the blob ids from the \`ls-files --stage\` output already in hand, or from one \`ls-files -s\` of the listed paths. Then read all of them in one \`cat-file --batch\` call fed through \`input\`, checking each size against MAX\_ATTR\_BYTES from the batch header. Alternatively, put a deadline on the whole call that covers every git child.

## Low (1)

- **Timeout/overflow messages name the command as 'git -c' instead of the subcommand** — `src/lib/kit/safe-git.js:231` (other): exec puts the -c overrides in front of the argv, so args\[0\] is always '-c'. A FIFO .gitattributes with \`safe-git --timeout 2000 -- status\` prints 'kit: git -c took longer than 2000 ms and was stopped'. The ENOBUFS message reads 'git -c wrote more than 256 MiB' in the same way. The user cannot tell which step timed out: the config read, the index listing, the attributes listing or their own command. The test at test/...test.js:1707 checks only the 'took longer than' part. — fix: Name the first argument that is not a -c pair, i.e. the subcommand after the overrides (or pass a label from the caller), and assert it in the existing timeout test.
