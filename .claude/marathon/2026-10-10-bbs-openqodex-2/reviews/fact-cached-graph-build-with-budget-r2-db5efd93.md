## Medium (3)

- **validFacts does not bounds-check def/call indices, so a corrupt cache entry crashes every later build** — `src/lib/kit/graph.js:821` (correctness): validFacts checks only that defs\[\].up and calls\[\].owner are integers. resolveGraph then dereferences them: facts.defs\[u\].up at line 999 and fi.nodes\[owner\].id at line 1128. Reproduced: run graph once in a small repo, change calls\[0\].owner to 7 (or defs\[0\].up to 9) in a cache file while keeping v and key, then run graph again. It exits 1 with 'Cannot read properties of undefined (reading 'id')' (or 'reading 'name''). The entry is never replaced, so every later run crashes the same way until someone deletes the cache by hand. The header promises that a cache file 'of the wrong shape is a miss, never trusted'. — fix: In validFacts, require -1 \<= d.up \< k for each def (it must point to an earlier def) and -1 \<= c.owner \< defs.length for each call; anything else is a miss.
- **One refused cache entry turns the cache off for the whole run, and for every later run** — `src/lib/kit/graph.js:914` (correctness): cacheGet calls cacheFail (cacheOn = false) on any code-2 refusal of a single entry, not only when the cache folder itself is refused. Two ways to trigger it. (a) Size mismatch: entries are written with guardedWrite's 64 MiB limit but read with maxCacheBytes (16 MiB). Reproduced with a 1 MB source of 'a()()' lines (inside maxFileBytes): its entry is 23 MB, is written on the first run, and is refused on every run after. (b) A single symlinked entry file. In both cases cache\_hits drops to 0 for every file scanned after it. With --max-parses 1 the other files land in not\_read as parse\_cap and partial becomes true, even though their facts are cached. The bad entry is never rewritten, because cachePut is skipped once the cache is off. — fix: In cacheGet, treat a refusal of one entry file as a miss and keep the cache on; call cacheFail only for a folder-level refusal. Also cap cachePut at o.maxCacheBytes (pass maxBytes to guardedWrite) so the cache never writes an entry it will refuse to read.
- **normalizeRel on git's own file list fails the whole build on a 'c:' name and silently drops names with backslashes** — `src/lib/kit/graph.js:847` (correctness): buildGraph runs normalizeRel on every path from git ls-files (line 874), not only on paths the user gave. On Linux, a legal top-level file such as 'c:notes.txt' (any extension, even one that is not source) matches /^\[A-Za-z\]:/, and the verb exits 1 with 'is not a path inside the repository' (reproduced). A file named 'src/we\ird.js' is rewritten to 'src/we/ird.js', which does not exist. It is counted only in stats.missing and is not listed in not\_read, and the result says partial:false while a source file was never read (reproduced). — fix: Use git's -z output as-is (it is already top-relative POSIX). Apply the drive-letter and backslash handling only to user-supplied --changed paths. Alternatively, put a path that cannot be normalised in not\_read with a reason instead of throwing or rewriting it.

## Low (2)

- **cache\_error is cut to 200 characters, so the reason is lost behind the long absolute path** — `src/lib/kit/graph.js:905` (other): guardedRead/guardedWrite messages start with the full absolute cache-file path, a 64-character hash plus the repo path. slice(0, 200) leaves only that path. Reproduced: cache\_error ended in '...cd01c3...f995.json is l' and '...json is a', so the reader cannot tell whether the cause was a size limit, a symlink or something else. — fix: Store the reason separately from the path (for example a code plus the basename), or cut from the start of the message rather than the end.
- **changed.requested counts changed files that are not source, so read \< requested looks like a gap** — `src/lib/kit/graph.js:1318` (facts): requested is the size of the set of all changed paths, which includes .md, .json and similar files. read counts only parsed source files. Reproduced: a diff touching 4 JS files and 1 non-source file reports requested 5, read 4, and nothing in not\_read explains the difference. w-review.md describes 'changed' as how many of the changed files were read, so a reviewer will look for a missing file that was never a candidate. — fix: Count requested over changed files that are source files (sourceSet), or report a separate ignored count.
